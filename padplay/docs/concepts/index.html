Concepts

日本語

PadPlay SDK turns a phone into a controller with a second screen: a touch screen that shows its own view of the game, plus a gyro and on-screen buttons. This page explains how it is put together and why, so the behavior you see in Quick Start is not a surprise.

Where the ideas come from

The SDK grew out of the student project that inspired it — a two-player co-op game played on a big screen plus a tablet with a hand-made controller and a gyro sensor. On the tablet, one player looked into the comic-panel world by tilting it, and touched the game directly. Making that work taught a handful of lessons, and each of them is now a part of the SDK:

  • Debugging was only possible with the special hardware in one room. → Touch is injected as standard uGUI events, so the mouse works identically.
  • A transparent touch layer over the streamed picture felt instant. → The phone app has two layers: video behind, a transparent touch layer in front.
  • Window size and resolution kept changing. → Touch is sent as normalized coordinates (0…1).
  • Several wireless controllers cross-talked unless each was addressed by name. → Each phone gets a player slot; a token in the QR code decides who may join.
  • Masked images blocked rays and transparent pixels were hit. → A custom raycaster with per-player screens and alpha hit testing.
  • The controller was exposed as a custom Input System device. → Each phone is a PadPlayPad, which is a Gamepad.
  • External streaming tools and custom hardware were fragile. → Video is streamed by the SDK itself (PadPlay Link, H.264 or JPEG); the phone's own sensors replace the hardware.

The big picture

 PHONE (PadPlay app)                            PC (Unity)

 touch layer (front, 0..1) --+                  PadPlayHost (slots, tokens, clocks)
 buttons (game's layout) ----+-- state ------>    touch     -> your uGUI handlers
 gyro (rotation vector) -----+   every 8 ms       PadPlayPad -> your InputActions,
                                 (latest only)                  Gyro Camera / Pointer

Core and Unity

The package has two assemblies (the names matter only when your own asmdef references them):

  • PadPlay.Core assembly — plain C# (C# 9, netstandard2.1, no engine references): the protocol, sessions, PadPlay Link (one encrypted UDP port), coordinate mapping, attitude math, clock sync, QR encoding. Everything that can be tested without Unity lives here, so other engines can reuse it later.
  • PadPlay.Unity assembly — everything that touches Unity: PadPlayHost, event injection, the raycaster, the Input System device, video, gyro components and UI helpers.

Both put the types you use in one namespace, PadPlay, so using PadPlay; is all you need, including for the few from Core (AttitudeCalibrationMode, ClockSync, DeviceInfo, PadPlayPhoneOverlayItem, PadPlayNetworkSettings). The rest of Core (packet encoders such as TouchPacket, PointerTracker, LinkHost, LinkClient) is internal to the package.

Modules

The host has four modules, ticked in its Inspector (host.Settings.Modules, a PadPlayModules flags value): Touch, Attitude, Buttons (including haptics) and Video. Each has its own settings object (Settings.Touch, Settings.Attitude, Settings.Buttons, Settings.Video).

The phone app always sends everything it has; the module switch works on the host side. An unticked module's input is dropped before it reaches uGUI, the events or the PadPlayPad, and nothing is sent for it (no layout, no vibration, no video). The Debugger still counts what arrives, so "the phone sends nothing" and "the module is off" look different.

Connecting: the QR code and player slots

 Unity (PadPlayHost)                                        Phone (PadPlay app)

 StartHost: join URL with a fresh token and key
 QR code  padplay://join?v=1&h=…&p=7780&t=…&k=…   ------>   scans it
                <------  UDP Hello (token, device info, capabilities), sealed with k
 Accept: player slot (PlayerJoined, PlayerReady)  ------>
                <------  touch / gyro / buttons: the whole state every 8 ms
                <------  touch down/up, button changes (reliable)
 layout / haptics / recenter (reliable), video    ------>
  • The QR code contains the PC's LAN address, the UDP port, a token and a key k. Only phones presenting the current token are accepted. RenewToken() makes a new code; already-joined phones stay. A joined phone that drops right after a renewal may still come back to its slot with the old code for host.NetworkSettings.RenewGraceMs (60 s; 0 = off), but only with the resume secret it received when it joined: the device id alone is not enough, and new phones always need the new code. This return has no fresh key exchange, so it is weaker than a normal join (a known limitation, to be fixed in 1.x); set RenewGraceMs to 0 if you renew the code to keep someone out.
  • Each accepted phone gets a player slot (0, 1, 2 …). Every input event, every PadPlayPointerEventData and every PadPlayPad carries that slot, so two players never mix.
  • If a phone drops without saying goodbye (Wi-Fi blip, app sent to background or closed), its slot is held for ResumeHoldSeconds (60 s). When it comes back it gets the same slot and the same PadPlayPad device (PlayerJoined with Resumed = true). The app keeps a per-game resume key and a device id, so this also works after the app was closed and started again. PlayerLeft.Reason tells you why a phone left (PadPlayLeaveReason: Bye, Closed, Timeout, Stopped, …).
  • When the slot is free for good — the player said bye, the host stopped, or the hold time ran out — PlayerRemoved fires (Reason Bye, Stopped or Expired). The hold time is counted in Core, in one place; GetPlayerState(slot) returns Connecting, Ready, Reconnecting or Gone.
  • AcceptNewPlayers = false closes the lobby: new phones are refused as "full", held slots can still resume.
  • Only the same LAN is supported. No STUN/TURN servers are used.

Encryption

Every packet after the QR code is encrypted and authenticated with ChaCha20-Poly1305. The key k is random, made anew on every StartHost and RenewToken, and only travels inside the QR code — never over the network. Each connection derives its own keys from it (HKDF-SHA256), and every packet carries a sequence number, so packets that were changed, replayed or sealed with another key are dropped and counted. Someone on the same Wi-Fi who has not seen the QR code can therefore neither read nor fake touches, buttons, the attitude or the video, nor take over a player's slot. What it does not hide: that traffic exists, its size and timing. It does not protect against people who can see the QR code (they can join, like anyone you show it to) or against jamming the Wi-Fi. Only two short "cannot join" answers (other protocol version; a code that does not match) are sent unencrypted, so that a phone with an old QR code is told so at once; they carry no game data.

There is no setting that turns encryption off, so a game cannot ship without it by mistake. The cryptography is implemented in the package from the public specifications (RFC 8439, RFC 5869, FIPS 180-4), with no third-party code and no allocation per packet.

State and reliable messages

  • state (Data) — every 8 ms, no retransmission. Carries: touch, attitude, buttons — the whole current state each time, so a lost packet is replaced by the next
  • reliable messages — resent until acknowledged, ordered. Carries: touch down/up and button changes (so a tap or a press is never lost), layout, haptics, calibration, screen orientation, video settings

Old or duplicated packets are dropped by sequence number. Your code only sees the events in order, on the main thread. A button press that arrives late as a reliable message is still applied once (then the current state), and the pad changes a given button at most once per Input System update, so a press and release in the same frame are both seen.

Touch

Two layers and normalized coordinates

On the phone the video sits behind a transparent touch layer. The touch layer reacts immediately (the finger does not wait for the video round trip) and reports each finger as (0, 0)–(1, 1) relative to the video area, letterbox excluded, with y pointing down (top-left origin). The Host maps it to pixels of whatever that player is looking at — Display 1, a rectangle of a display, or a camera — so resolution and window size never shift touches.

Injected as standard events

The SDK does not replace your input module. For each finger it keeps its own PointerEventData (PadPlayPointerEventData) and calls the same ExecuteEvents handlers an input module would: OnPointerEnter/Exit/Down/Up/Click, OnBeginDrag/OnDrag/OnEndDrag, … with the usual drag threshold and click timing. Consequences:

  • Existing Buttons, Sliders and IDragHandlers work without changes.
  • The mouse keeps working at the same time, with its own pointer data. You can develop without a phone.
  • To know who touched, test eventData is PadPlayPointerEventData p and read p.PlayerSlot.
  • Pointer ids are allocated far away from mouse and local-touch ids, so they never collide.

Per-player screens and the raycaster

When several players each see their own view (split screen, Display 2, or a video sent to their phone), a touch must only hit what that player sees. The dispatcher runs the normal EventSystem.RaycastAll and then keeps only results from raycasters that belong to the player's screen (decided by BaseRaycaster.eventCamera).

PadPlayRaycaster is a drop-in GraphicRaycaster that additionally ignores hits on transparent pixels of an Image (AlphaThreshold, default 0.1). It works for Screen Space and World Space canvases and for the mouse.

Gamepad, gyro and buttons

PadPlayPad is a Gamepad

Each ready phone becomes an Input System device PadPlayPad : Gamepad. Inheriting from Gamepad means existing <Gamepad>/… bindings, Gamepad.all and PlayerInput control schemes work unchanged. It adds the controls attitude, angularVelocity, playerSlot and game-defined buttons custom14…custom31 (lower-case, like other Input System controls); C# values are PascalCase (PlayerSlot, IsConnected, ButtonBits, GetButton(id)). The pad exists from just before PlayerReady until just before PlayerRemoved. Gyro controls are marked noisy, so holding the phone does not steal Gamepad.current. The device runs in the background, so input keeps arriving when the PC window loses focus. Rumble (SetMotorSpeeds) drives the phone's vibration.

Attitude

The phone sends its Game Rotation Vector (a quaternion fused from gyro and accelerometer, without the magnetometer — the same choice the original project made with its sensor) and angular velocity. The SDK converts it to Unity's left-handed space, where identity = phone upright in portrait, screen facing you, and:

  • calibrates yaw on connect (the direction the player faces becomes forward);
  • smooths over network jitter: samples carry the phone's timestamp; with the clock offset (measured from the timestamps that every packet echoes back) the SDK extrapolates a short way and blends corrections in, so the camera does not stutter when packets bunch up.

PadPlayGyroCamera and PadPlayGyroPointer sit on top of this. Their re-centering is local to the component, so it does not change the pad's attitude that other code reads.

Naming: components you add are called Gyro (PadPlayGyroCamera); the data is called attitude (AttitudeReceived, pad.attitude, the Attitude module). Every calibration takes one enum, AttitudeCalibrationMode (Yaw or Full).

Coordinates: phone positions (PadPlayPointerEventData.PhonePosition, layouts) have y = 0 at the top; the gyro pointer's ViewportPosition is Unity viewport space with y = 0 at the bottom. The names say which.

Buttons are a layout the game sends

The phone has no fixed button set. The game sends a layout — ids, shapes, centers and sizes in the same 0…1 video-area coordinates as touch — and the phone draws it above the touch layer. Fingers that start on a button go to the button — or within 2.5 mm of its edge, to the nearest button (a setting of the app, not of the layout); all others are touches. Pressed bits and stick values come back in the state and land in the PadPlayPad. Changing the layout asset while playing resends it, so positions can be tuned by hand.

Each element can also carry a style: colors, border, corners, label size and pictures (PadPlayButtonStyle). The layout names pictures by a hash of their PNG; the phone asks only for the ones it does not keep yet, receives them over the same encrypted channel one piece at a time (input and haptics are never held up), and keeps them for the next connection. Until a picture arrives the button is drawn with its colors (Quick Start: Button looks).

Second screen (video)

PadPlayView streams a camera or RenderTexture to one player (or to everyone) over PadPlay Link, on the same UDP port as the input. Adding or changing a view while connected only switches that player's video (the connection, the slot and the pad stay; PlayerReady does not fire again). Cameras that nobody watches are disabled, and nothing is encoded while nobody watches.

Codec. H.264 from Windows Media Foundation (the GPU's hardware encoder when one works, otherwise Windows' software encoder), or JPEG (Unity's own JPEG encoder; the phone app decodes it with Flutter). With Settings.Video.Codec = Auto, every player starts with H.264; the phone measures how fast it decodes H.264 and asks for JPEG when it is too slow (or when the app knows the model needs it), and the host switches that player only. A host without H.264 sends JPEG to everyone. The SDK bundles no codec of its own (see Video codecs in the package README). host.GetVideoChoice(slot, out choice) tells which codec a player gets and why.

Graphics APIs. Direct3D 11 and Direct3D 12 hand the rendered frame to the encoder without leaving the GPU (Direct3D 12 through a shared texture and fence). Vulkan reads the frame back to the CPU first (about one frame later). OpenGL, macOS and Linux have no H.264 path and send JPEG. host.VideoStatus shows the path, the encoder and the reason when H.264 is not used.

Weak Wi-Fi. Lost pieces of a frame are repaired with Reed-Solomon forward error correction, which grows with the measured loss. What cannot be repaired is fixed with a small recovery frame that refers to an older frame the phone still has (when the encoder supports it), and only then with a key frame. The phone shows the newest complete frame and waits (at most Max Playout Frames) only while frames arrive unevenly. With Adaptive Video the host watches each player's loss, delay and received rate: it lowers the bitrate at once when the network is congested, then the frame rate or the size (Priority), and raises them again slowly. When frames that could not be repaired come close together (typical of 2.4 GHz Wi-Fi, where losses come in bursts), it lowers the bitrate early even if the average loss is small. A view sent to several players is encoded once, at the quality of the weakest connection. The SDK shows nothing about this to players; host.GetConnectionQuality(slot) and ConnectionQualityChanged let your game show its own hint.

Across scenes

By default a PadPlayHost lives in its scene: loading another scene destroys it and every phone is disconnected. Tick Keep Across Scenes on the Host (for example in your title or menu scene) to keep the phones connected while you switch scenes — same player slots, same encryption keys, same PadPlayPad devices, no QR code to scan again.

  • The first such Host creates a kept Host on its own GameObject in DontDestroyOnLoad (PadPlayHost.KeptHost) and hands its settings to it. From then on, the Host of every scene you load hands its settings to the kept Host and steps aside — whether or not it has Keep Across Scenes ticked. So each scene keeps its own Host, works when opened on its own, and never ends up with two.
  • The kept Host uses the settings of the scene's Host: the button layout is sent to the phones again, modules apply (a scene without the Video module stops the video; a PadPlayView in the new scene starts it), and Max Players limits new players. Lowering it does not disconnect anyone already playing; new phones are refused as full until a slot below the limit is free. Per-player layouts (SetLayout) and phone overlays from the previous scene are cleared. The connection values (Port, Game Name, Resume Hold Seconds, NetworkSettings) stay those of the first Host.
  • Where each player last recentered is kept too: Remote Pointers or a Gyro Pointer in the next scene starts from it, so the cursor does not jump to the center and the player does not have to recenter again.
  • Every member of a scene's Host goes to the kept Host, so the scene's components and your scripts keep using "their" Host. Event handlers added through a scene's Host are removed when that scene unloads. Objects that outlive scenes (a DontDestroyOnLoad manager) should subscribe to PadPlayHost.KeptHost (or host.ActiveHost) instead.
  • To drop the phones on purpose, call StopHost() (on any of them), or destroy PadPlayHost.KeptHost.gameObject.
// Menu scene: its Host has Keep Across Scenes ticked. A demo scene has its own Host (any settings).
SceneManager.LoadScene("Demo");      // phones stay connected; the Demo Host's layout and modules apply
// ...later, from the demo:
SceneManager.LoadScene("Menu");      // back to the menu's layout; still the same players

// A manager that lives across scenes listens on the kept Host:
PadPlayHost.KeptHost.PlayerJoined += p => Debug.Log($"P{p.PlayerSlot + 1} joined");

The Editor's Virtual Phones stay connected across scenes too. In PadPlay Lite it works the same (one player, no video).

Editions: PadPlay SDK and PadPlay Lite

PadPlay Lite (free) is the same package and works the same way, but leaves out: more than one player (Max Players is capped at 1), second-screen video (PadPlayView and the encoder are not included, so the Video module does nothing), the samples other than Sample Hub (with Target Pop) and Minimal, and the phone app source code. PadPlayEdition.IsLite tells your code which one it runs in.

Tuning by feel

Latency, smoothing, sensitivity and dead zones cannot be judged on paper. Every such value is a field in an Inspector settings object (Settings.Touch, Settings.Attitude, Settings.Buttons, the gyro components' Settings, the button layout) and most can be changed while playing. Defaults are starting points, not final answers. Use the Display preview and the Debugger (Debugging) to see the numbers while you tune.
