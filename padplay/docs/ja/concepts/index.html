仕組み

English

PadPlay SDK は、スマホを第二画面つきのコントローラーにします。ゲームの画面をスマホごとに出すタッチパネルに、ジャイロと画面のボタンが加わります。このページでは、それが どう 組み立てられているか、なぜ そうしたのかを説明します。クイックスタート で見る動きに戸惑わないための背景です。

考え方の出どころ

この SDK は、もとになった学生時代のプロジェクトから生まれました。大きな画面と、自作のコントローラーとジャイロセンサーを付けたタブレットで遊ぶ、2 人協力のゲームです。タブレットを持つ人は、それを傾けて漫画のコマの世界を のぞき込み、ゲームに直接触れて操作しました。これを動かすまでにいくつかの教訓を得ていて、そのひとつひとつが今の SDK の一部になっています:

  • 特別なハードウェアがある 1 部屋でしかデバッグできなかった。 → タッチを uGUI の標準のイベント として流し込むので、マウスでもまったく同じに動きます。
  • 送られてくる絵の上に透明なタッチの層を重ねると、反応がすぐに感じられた。 → スマホのアプリは 2 層: 奥に映像、手前に透明なタッチの層。
  • 窓の大きさや解像度がたびたび変わった。 → タッチは 正規化した座標(0〜1)で送ります。
  • 無線のコントローラーを複数使うと、名前で指定しない限り混線した。 → スマホごとに プレイヤー枠 を割り当て、QR コードの中のトークン で参加できる端末を決めます。
  • マスクした画像がレイを遮り、透明なピクセルにも当たってしまった。 → プレイヤーごとの画面とアルファでの当たり判定を持つ 独自の Raycaster。
  • コントローラーを独自の Input System のデバイスとして見せていた。 → スマホはそれぞれ PadPlayPad で、これは Gamepad そのもの です。
  • 外部の配信ツールと自作のハードウェアは壊れやすかった。 → 映像は SDK 自身が送ります(PadPlay Link、H.264 か JPEG)。ハードウェアの代わりにスマホのセンサーを使います。

全体像

 PHONE (PadPlay app)                            PC (Unity)

 touch layer (front, 0..1) --+                  PadPlayHost (slots, tokens, clocks)
 buttons (game's layout) ----+-- state ------>    touch     -> your uGUI handlers
 gyro (rotation vector) -----+   every 8 ms       PadPlayPad -> your InputActions,
                                 (latest only)                  Gyro Camera / Pointer

 buttons, vibration  <-- reliable messages --   PadPlayHost (layout, haptics, recenter)
 video layer (back)  <-- H.264 / JPEG, FEC ---  PadPlayView (camera / RenderTexture)

Core と Unity

パッケージには 2 つのアセンブリがあります(名前が関係するのは、自分の asmdef から参照する時だけです):

  • PadPlay.Core アセンブリ — エンジンを参照しない素の C#(C# 9、netstandard2.1): プロトコル、セッション、PadPlay Link(暗号化した 1 つの UDP ポート)、座標の変換、姿勢の計算、時計の同期、QR のエンコード。Unity なしでテストできるものは全部ここに置いているので、後でほかのエンジンからも使えます。
  • PadPlay.Unity アセンブリ — Unity に触れるもの全部: PadPlayHost、イベントの流し込み、Raycaster、Input System のデバイス、映像、ジャイロの部品、UI の補助。

どちらも、使う型を 1 つの名前空間 PadPlay に入れているので、using PadPlay; だけで足ります。Core の一部の型(AttitudeCalibrationMode、ClockSync、DeviceInfo、PadPlayPhoneOverlayItem、PadPlayNetworkSettings)も同じです。Core のそれ以外(TouchPacket などのパケットのエンコーダー、PointerTracker、LinkHost、LinkClient)はパッケージの内部用です。

モジュール

ホストには 4 つのモジュールがあり、Inspector でチェックを入れて使います(host.Settings.Modules、PadPlayModules のフラグの値):Touch(タッチ)、Attitude(姿勢)、Buttons(ボタン。振動を含む)、Video(映像)。それぞれに設定のオブジェクトがあります(Settings.Touch、Settings.Attitude、Settings.Buttons、Settings.Video)。

スマホのアプリは持っているものをいつも全部送ります。モジュールのオン・オフはホスト側で効きます。チェックを外したモジュールの入力は、uGUI・イベント・PadPlayPad に届く前に捨てられ、そのモジュールのためには何も送りません(レイアウトも振動も映像も送りません)。デバッガーは届いたものを数え続けるので、「スマホが何も送っていない」のか「モジュールがオフ」なのかを見分けられます。

接続: QR コードとプレイヤー枠

 Unity (PadPlayHost)                                        Phone (PadPlay app)

 StartHost: join URL with a fresh token and key
 QR code  padplay://join?v=1&h=…&p=7780&t=…&k=…   ------>   scans it
                <------  UDP Hello (token, device info, capabilities), sealed with k
 Accept: player slot (PlayerJoined, PlayerReady)  ------>
                <------  touch / gyro / buttons: the whole state every 8 ms
                <------  touch down/up, button changes (reliable)
 layout / haptics / recenter (reliable), video    ------>
  • QR コードには、PC の LAN のアドレス、UDP ポート、トークン、鍵 k が入っています。受け入れるのは、今のトークンを示したスマホだけです。RenewToken() で新しいコードになります。参加済みのスマホはそのままです。作り直しの直後に切れた参加済みのスマホは、host.NetworkSettings.RenewGraceMs(60 秒。0 = オフ)の間なら古いコードで自分の枠に戻れますが、それには参加した時に受け取った再開用の秘密の値が要ります。端末の ID だけでは戻れず、新しいスマホにはいつも新しいコードが要ります。この戻り方は鍵の交換をやり直さないので、ふつうの参加より守りが弱くなります(分かっている制限で、1.x で直す予定です)。誰かを締め出すためにコードを作り直す時は、RenewGraceMs を 0 にしてください。
  • 受け入れたスマホには、それぞれ プレイヤー枠(0、1、2 …)を割り当てます。入力のイベント、PadPlayPointerEventData、PadPlayPad のどれにもその枠の番号が付いているので、2 人の入力が混ざることはありません。
  • スマホが別れのあいさつなしに切れた場合(Wi-Fi が一瞬切れた、アプリが裏に回った・閉じられた)、その枠はResumeHoldSeconds(60 秒)の間 取っておきます。戻ってくると、同じ枠と同じ PadPlayPad のデバイスを受け取ります(Resumed = true の PlayerJoined)。アプリはゲームごとの再開用の鍵と端末の ID を覚えているので、アプリを閉じて起動し直した後でも戻れます。PlayerLeft.Reason で、スマホが抜けた理由が分かります(PadPlayLeaveReason: Bye、Closed、Timeout、Stopped など)。
  • 枠が本当に空いた時(プレイヤーが bye を送った、ホストが止まった、取っておく時間が過ぎた)は、PlayerRemovedが出ます(Reason は Bye・Stopped・Expired)。取っておく時間は Core の 1 か所で数えています。GetPlayerState(slot) はConnecting・Ready・Reconnecting・Gone のどれかを返します。
  • AcceptNewPlayers = false でロビーを閉じます。新しいスマホは「満員」として断り、取っておいた枠には戻れます。
  • 対応しているのは同じ LAN の中だけです。STUN/TURN のサーバーは使いません。

暗号化

QR コードより後のパケットは、全部 ChaCha20-Poly1305 で暗号化・認証しています。鍵 k は乱数で、StartHost と RenewToken のたびに作り直し、QR コードの中でしか運ばれません(ネットワークは流れません)。接続ごとにそこから専用の鍵を導き(HKDF-SHA256)、パケットには通し番号が付いているので、書き換えられたパケット・再送されたパケット・別の鍵で封をしたパケットは捨てて数えます。そのため、同じ Wi-Fi にいても QR コードを見ていない人は、タッチ・ボタン・姿勢・映像を読むことも偽ることもできず、プレイヤーの枠を乗っ取ることもできません。隠さないもの: 通信があること、その大きさとタイミング。QR コードを見られる人(見せた相手と同じように参加できます)や、Wi-Fi の妨害は防げません。「参加できない」ことを伝える短い返事 2 つ(プロトコルの版が違う、コードが合わない)だけは暗号化せずに送ります。古い QR コードを使ったスマホにすぐ伝えるためで、ゲームのデータは入っていません。

暗号化を切る設定は無いので、うっかり暗号化なしでゲームを出してしまうことはありません。暗号は公開されている仕様(RFC 8439、RFC 5869、FIPS 180-4)からパッケージの中に実装していて、外部のコードは使っておらず、パケットごとのメモリの確保もありません。

状態と確実に届くメッセージ

  • 状態(Data) — 8 ms ごと、再送なし。運ぶもの: タッチ・姿勢・ボタン。毎回今の状態を丸ごと送るので、1 つ失っても次のパケットで置き換わります
  • 確実に届くメッセージ — 受け取りの返事が来るまで再送、順番どおり。運ぶもの: タッチの押した・離した、ボタンの変化(タップや押下を失わないため)、レイアウト、振動、校正、画面の向き、映像の設定

古いパケットや重なったパケットは、通し番号で捨てます。ゲームのコードには、イベントが順番どおりにメインスレッドで届きます。確実に届くメッセージとして遅れて届いたボタンの押下も 1 回は反映し(その後に今の状態を反映します)、パッドは 1 つのボタンを Input System の1 回の更新につき 1 回までしか変えないので、同じフレームの押した・離したの両方が見えます。

タッチ

2 つの層と正規化した座標

スマホでは、映像は透明なタッチの層の奥にあります。タッチの層はすぐに反応し(指は映像の往復を待ちません)、指の位置を映像の領域に対する (0, 0)〜(1, 1) で送ります。上下左右の黒い帯は含まず、y は下向き(左上が原点)です。ホストはそれを、そのプレイヤーが見ている物(Display 1、ディスプレイの中の四角形、カメラ)のピクセルに直すので、解像度や窓の大きさが変わってもタッチはずれません。

標準のイベントとして流し込む

SDK は入力モジュールを置き換え ません。指ごとに専用の PointerEventData(PadPlayPointerEventData)を持ち、入力モジュールが呼ぶのと同じ ExecuteEvents のハンドラーを呼びます:OnPointerEnter/Exit/Down/Up/Click、OnBeginDrag/OnDrag/OnEndDrag など。ドラッグ開始距離とクリックのタイミングもいつもどおりです。その結果:

  • 今ある Button・Slider・IDragHandler が、変えずに動きます。
  • マウスも同時に、自分のポインターのデータで動きます。スマホなしで開発できます。
  • 誰が 触ったかは、eventData is PadPlayPointerEventData p を調べて p.PlayerSlot を読みます。
  • ポインターの ID は、マウスやローカルのタッチの ID から遠く離れた所で割り当てるので、ぶつかりません。

プレイヤーごとの画面と Raycaster

複数のプレイヤーがそれぞれ自分の画面を見ている時(画面の分割、Display 2、スマホに送る映像)、タッチは そのプレイヤー が見ている物にだけ当たる必要があります。振り分けでは、いつもの EventSystem.RaycastAll を行い、そのプレイヤーの画面に属する Raycaster の結果だけを残します(BaseRaycaster.eventCamera で決めます)。

PadPlayRaycaster は GraphicRaycaster と差し替えて使える Raycaster で、Image の 透明なピクセル への当たりを無視します(AlphaThreshold、既定 0.1)。Screen Space と World Space の Canvas の両方で、マウスにも効きます。

Gamepad・ジャイロ・ボタン

PadPlayPad は Gamepad

準備完了になったスマホは、それぞれ Input System のデバイス PadPlayPad : Gamepad になります。Gamepad を継承しているので、今ある<Gamepad>/… のバインド、Gamepad.all、PlayerInput のコントロールスキームがそのまま動きます。加えて、コントロール attitude・angularVelocity・playerSlot と、ゲームが決めるボタン custom14〜custom31 があります(ほかの Input System のコントロールと同じく小文字です)。C# の値は PascalCase です(PlayerSlot、IsConnected、ButtonBits、GetButton(id))。パッドは PlayerReady の直前からPlayerRemoved の直前まであります。ジャイロのコントロールには noisy の印を付けているので、スマホを持っているだけでGamepad.current を取ってしまうことはありません。デバイスはバックグラウンドでも動くので、PC の窓からフォーカスが外れても入力は届き続けます。振動(SetMotorSpeeds)はスマホのバイブレーションを動かします。

姿勢

スマホは Game Rotation Vector(ジャイロと加速度センサーから求めた、地磁気センサーを使わないクォータニオン。もとのプロジェクトでセンサーに選んだのと同じ方式です)と角速度を送ります。SDK はこれを Unity の左手系に直し(単位回転 = スマホを縦向きにまっすぐ立て、画面を自分に向けた状態)、さらに:

  • 接続した時にヨーを校正 します(プレイヤーが向いている方向が正面になります)。
  • ネットワークの揺らぎをならします: 標本にはスマホの時刻が付いています。時計のずれ(パケットが毎回返す時刻の印から測ります)を使って、SDK は少し先まで外挿し、ずれの修正はなじませながら入れるので、パケットがまとめて届いてもカメラがカクつきません。

PadPlayGyroCamera と PadPlayGyroPointer はこの上に乗っています。これらの正面合わせは部品の中だけで効くので、ほかのコードが読むパッドの姿勢は変わりません。

名前の付け方: 付ける部品は Gyro(PadPlayGyroCamera)、データは attitude(姿勢。AttitudeReceived・pad.attitude・Attitude のモジュール)と呼んでいます。校正はどれも 1 つの列挙型 AttitudeCalibrationMode(Yaw か Full)を取ります。

座標: スマホの上の位置(PadPlayPointerEventData.PhonePosition、レイアウト)は y = 0 が上 です。Gyro Pointer の ViewportPosition は Unity のビューポートの座標で、y = 0 が下 です。どちらかは名前で分かるようにしています。

ボタンはゲームが送るレイアウト

スマホには決まったボタンの組はありません。ゲームが レイアウト(ID・形・中心・大きさ。タッチと同じ 0〜1 の映像の領域の座標)を送り、スマホはそれをタッチの層の上に描きます。ボタンの上で触り始めた指はそのボタンに行きます。ボタンの縁から 2.5 mm 以内なら、一番近いボタンに行きます(これはアプリの設定で、レイアウトの設定ではありません)。それ以外はタッチです。押されたビットとスティックの値は状態に入って戻り、PadPlayPad に入ります。再生中にレイアウトのアセットを変えると送り直すので、位置を手で調整できます。

要素はそれぞれ 見た目(色・縁・角・文字の大きさ・画像。PadPlayButtonStyle)も持てます。レイアウトは画像をその PNG のハッシュで指し、スマホはまだ持っていない画像だけを頼みます。画像は同じ暗号の経路で一切れずつ届き(入力と振動を待たせません)、スマホは次につなぐ時のために覚えます。画像が届くまでは、そのボタンを色で描きます(クイックスタート: ボタンの見た目)。

第二画面(映像)

PadPlayView は、カメラか RenderTexture を 1 人のプレイヤー(または全員)へ、入力と同じ UDP ポートで PadPlay Link を通して送ります。つながっている間に View を足したり変えたりしても、切り替わるのはそのプレイヤーの映像だけです(接続・枠・パッドはそのままで、PlayerReady はもう一度は出ません)。誰も見ていないカメラは止め、誰も見ていない間は何もエンコードしません。

コーデック。 Windows Media Foundation の H.264(GPU のハードウェアエンコーダーが使えればそれ、無ければ Windows のソフトウェアエンコーダー)か、JPEG(Unity の JPEG のエンコーダー。スマホのアプリは Flutter で復号します)。Settings.Video.Codec = Auto なら、どのプレイヤーも H.264 で始めます。スマホは H.264 の復号の速さを測り、遅すぎれば(またはアプリがその機種には要ると知っていれば)JPEG を求め、ホストはそのプレイヤーだけを切り替えます。H.264 を使えないホストは、全員に JPEG を送ります。SDK は独自のコーデックを同梱していません(パッケージの README の Video codecs を参照)。host.GetVideoChoice(slot, out choice) で、プレイヤーがどのコーデックを受けていて、その理由が分かります。

グラフィックス API。 Direct3D 11 と Direct3D 12 は、描いたフレームを GPU から出さずにエンコーダーへ渡します(Direct3D 12 は共有のテクスチャとフェンスを使います)。Vulkan は一度フレームを CPU に読み戻します(1 フレームほど遅れます)。OpenGL・macOS・Linux には H.264 の経路が無く、JPEG で送ります。host.VideoStatus で、経路・エンコーダー・H.264 を使わない理由が分かります。

弱い Wi-Fi。 フレームの失った断片は、Reed-Solomon の前方誤り訂正(FEC)で直します。訂正の量は、測った損失に合わせて増えます。直せない分は、スマホがまだ持っている古いフレームを参照する小さな復旧フレームで直し(エンコーダーが対応していれば)、それもできない時に初めてキーフレームを使います。スマホは一番新しい完全なフレームを出し、フレームの届き方にむらがある間だけ待ちます(最大 Max Playout Frames)。Adaptive Video がオンなら、ホストはプレイヤーごとの損失・遅れ・受け取れている量を見ています。ネットワークが混んだらすぐにビットレートを下げ、次にフレームレートか大きさ(Priority)を下げ、よくなればゆっくり戻します。複数のプレイヤーに送る View は 1 回だけエンコードし、一番弱い接続に合わせた画質になります。

シーンをまたぐ

既定では、PadPlayHost はそのシーンの中にあります。別のシーンを読むと Host は壊され、スマホは全部切れます。Host(例えばタイトルやメニューのシーンの物)で Keep Across Scenes(シーンをまたいで保つ)にチェックを入れると、シーンを切り替えてもスマホはつながったままです。プレイヤー枠も、暗号の鍵も、PadPlayPad のデバイスも同じで、QR コードを読み直す必要もありません。

  • このような最初の Host は、DontDestroyOnLoad の専用の GameObject に 残す Host(PadPlayHost.KeptHost)を作り、自分の設定をそこに預けます。それ以降は、Keep Across Scenes にチェックがあってもなくても、読み込んだシーンの Host は、どれも設定を残す Host に預けて 身を引きます。そのため、どのシーンにも自分の Host があり、そのシーンだけを開いても動き、Host が 2 つになることもありません。
  • 残す Host は、シーンの Host の設定を使います。ボタンの レイアウト はスマホへ送り直し、モジュール も効きます(Video のモジュールが無いシーンでは映像が止まり、新しいシーンに PadPlayView があれば映像が始まります)。Max Players は新しいプレイヤーの数を制限します。値を下げても、もう遊んでいる人は切りません。上限より下の枠が空くまで、新しいスマホを満員として断ります。プレイヤーごとのレイアウト(SetLayout)と、前のシーンの Phone Overlay は消します。接続の値(Port、Game Name、Resume Hold Seconds、NetworkSettings)は最初の Host の物のままです。
  • 各プレイヤーが最後に Recenter した向きも残ります。次のシーンの Remote Pointers や Gyro Pointer はその向きから始まるので、カーソルが真ん中に飛ばず、Recenter し直す必要もありません。
  • シーンの Host のメンバーは全部、残す Host に行くので、シーンの部品と自分のスクリプトは「自分の」Host をそのまま使えます。シーンの Host を通して足したイベントハンドラーは、そのシーンを閉じる時に外します。シーンより長く生きるオブジェクト(DontDestroyOnLoad のマネージャー)は、代わりに PadPlayHost.KeptHost(か host.ActiveHost)に登録してください。
  • わざとスマホを切るには、(どの Host でも)StopHost() を呼ぶか、PadPlayHost.KeptHost.gameObject を壊します。
// Menu scene: its Host has Keep Across Scenes ticked. A demo scene has its own Host (any settings).
SceneManager.LoadScene("Demo");      // phones stay connected; the Demo Host's layout and modules apply
// ...later, from the demo:
SceneManager.LoadScene("Menu");      // back to the menu's layout; still the same players

// A manager that lives across scenes listens on the kept Host:
PadPlayHost.KeptHost.PlayerJoined += p => Debug.Log($"P{p.PlayerSlot + 1} joined");

エディタの仮想スマホも、シーンをまたいでつながったままです。PadPlay Lite でも同じように動きます(1 人、映像なし)。

版: PadPlay SDK と PadPlay Lite

PadPlay Lite(無料)は同じパッケージで同じように動きますが、次の物がありません: 2 人以上のプレイヤー(Max Players の上限が 1)、第二画面の映像(PadPlayView とエンコーダーが入っていないので、Video のモジュールは何もしません)、Sample Hub(Target Pop つき)と*Minimal* 以外のサンプル、スマホのアプリのソース。PadPlayEdition.IsLite で、コードからどちらの版で動いているかが分かります。

触って調整する

遅れ・平滑化・感度・デッドゾーンは、机の上では決められません。このような値は全部 Inspector の設定のオブジェクトのフィールドにしてあり(Settings.Touch、Settings.Attitude、Settings.Buttons、ジャイロの部品の Settings、ボタンのレイアウト)、ほとんどは再生中に変えられます。既定の値は出発点で、最終的な答えではありません。調整する間は、Display のプレビューとデバッガー(デバッグ)で数字を見てください。
