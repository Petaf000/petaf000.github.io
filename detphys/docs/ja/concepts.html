#決定論的な同期とは

DetPhys の対戦は「物体の位置を送り合う」のではなく、「同じ入力を両方の端末で同じ順に入れて、同じ計算をする」ことでそろえます。物理（2D は Box2D v3、3D は Box3D）は、浮動小数点のままでも、決まったビルド設定（fast-math なし・FMA の自動合成なし・三角関数は自前）なら、x64 と arm64、MSVC と clang と gcc のどれでもビットまで同じ結果を出します。DetPhys はこれを、Unity・Godot・Unreal のどれからでも同じビルド済みのコアを呼ぶことで、エンジンをまたいで守ります。

そのために、ゲームの側に守ってもらう決まりがあります（4. 決定論を守るためのルール）。いちばん大事なのは「シミュレーションに入るものは全部整数」です。

#tick

  • シミュレーションは tick ごとに進みます。既定は 60 Hz（tick_hz 60）・1 tick に 4 サブステップ・重力 (0, −10000) mm/s²。
  • 各 tick の状態のハッシュ（64 bit、FNV-1a）は、tick の番号・ボディの数・ボディを作った順に、位置 (x, y)・回転 (cos, sin)・速度 (vx, vy)・角速度 w の float の生のビット列から作ります（detphys_world_hash。3D は位置 3・四元数 4・速度 3・角速度 3 で detphys3d_world_hash）。2 つのピアのハッシュが同じなら、状態は同じです。
  • ボディの ID は、そのワールドで作った順の通し番号（0 から）です。消しても詰めず、使い回しません。

#入力とゲームの状態

  • 入力は、ゲームが決める固定長の int32 の列です。ターン制は 1 ターンに 1〜64 語、リアルタイムは 1 ピア・1 tick に 1〜16 語。例: 積み上げは [落とす x (mm), 向き (mrad)]、押し合いは [移動 −100〜100, ボタンのビット]。
  • エンジンの float（マウスの位置・スティックの値）は、入力を作る端末で 1 回だけ整数にしてから渡します。整数にした後の値が両方の端末に届くので、量子化の誤差も両方で同じです。
  • ゲームの状態（状態ワード）は、ルールが持つ int32 の列です（0〜64 語）。点数・残り時間・手番の数など。ハッシュに入り、ロールバックでも戻ります。
  • ルールの設定（params）はセッションを作る時に写し取り、つなぐ時に相手と照合します。設定・形・形の順番・session id が違うピアとはつながりません（rt バージョン 7・turn バージョン 9 からは、どこが違うかが分かります。5. desync への対処）。

#ルール

ルールは、入力をワールドに入れるゲームのコードで、コールバックの組です。コアが、どのピアでも同じ順番・同じ回数で呼びます。

組み込みのルールもあります（どちらもコアの中にあり、コールバックを書かずにセッションを作れます）:

  • ターン制の積み上げ（detphys_turn_create_stack_ex）: 形を交互に落として積む。次の形はルールが seed・試合・ターンの番号から決めます。
  • リアルタイムの押し合い（detphys_rt_create_push）: 2 人のプレイヤーが箱と凹形状を押し合う。動くステージ（回る歯車・往復する足場・上下する U）を選べ、そのキネマティックの表はセッションが持ちます。Unity（DetPhysRtSession.CreatePush）と Godot（DetPhysRtSession.create_push）は同じこのルールを呼ぶので、Unity と Godot の間で対戦できます。ボディの番号は detphys_rule_push_get_layout で分かります。

Unity ではルールを C# で書けます（DetPhysRtRule、Mono と IL2CPP で動作。サンプルの CSharpPushRule が押し合いを C# で書いた例で、コアのルールと同じ結果になり互いにつながります）。C++ では detphys_rule.hpp の detphys::make_rule で、メンバー関数からターン制のルールを作れます。

#ターン制

1 ターンの流れ:

  1. 手番のピアが入力を出す（detphys_turn_submit_words）。入力は相手に送られます。
  2. 両方のピアが同じ入力で進めます。ターンの終わりは、ルールの after_tick が決めます（無ければ「動くボディが全部眠ったら」）。上限は max_ticks_per_turn（既定 900 tick = 60 Hz で 15 秒）。
  3. ターンの終わりの状態のハッシュを交換して照合します。
  4. desync していたら、ホスト（ピア 0）の状態が正です。ホストが full の snapshot を送り、ゲストを置き換えます（再同期）。
  • 再接続: ゲストのアプリが落ちたら、同じ設定でセッションを作り直して poll するだけです。ホストが今の状態を送り、同じターンから続けます。
  • ホストの再起動: ゲストは毎ターンの初めの状態を持っているので、ホストが作り直したセッションにそれを送り、そのターンの初めから両方で続けます。ホストが自分の手番で落ちた時は、ホストの打ち直しになります。
  • 相手から peer_timeout_ms（既定 5000）何も届かないと PEER_LOST を知らせますが、セッションは待ち続けます。やめるかどうかはアプリが決めます。
  • 通信量の目安: 積み上げで 1 ターン 2 ピア合計 150〜190 バイト。

#リアルタイム（ロールバック）

毎フレーム、自分の入力を渡して detphys_rt_advance を 1 回呼びます。相手の入力がまだ届いていない tick は予測して進めます。

  • 届いた入力が予測と違ったら、その tick の 1 つ前の状態にロールバック、今の tick まで再計算します。だから入力の遅延 0 でも、自分の操作はすぐ画面に出ます。
  • 両方の入力が届いて、その入力で計算した tick が確定 tick です。確定 tick のハッシュ（の下 32 bit）を相手に送って照合します（既定は毎 tick・1 つのハッシュを 2 つのパケットに載せる）。
  • desync したらホストが full の snapshot を送ってゲストを置き換えます（世代を 1 つ上げ、照合は同じ世代の tick だけで行います）。
  • 予測して進めてよいのは予測の上限 N（max_prediction、既定 10、0〜60）tick までです。超えそうな時は進めずに待ちます（DETPHYS_RT_STALLED）。
  • 相手より 1 tick 以上先に進んでいる側は 1 フレーム休みます（time sync、DETPHYS_RT_SYNC_WAIT）。
  • 描画は detphys_rt_world を読みます（予測を含む今の状態）。ロールバックで位置が飛ぶことがあるので、見た目だけなめらかにしてよいです（結果には影響しません）。
  • ルールのコールバックは、ロールバックのたびに同じ tick で何度も呼ばれます。ゲームの状態はワールドと状態ワードにだけ置きます（それ以外に持つとロールバックで戻りません）。音やエフェクトは ctx->resimulating が 1 の間は出さないようにします。
  • 通信量: 1 tick あたり片方向 32〜48 バイト（UDP / IP の見出しを除く）。未確認の入力をまとめて載せるので、取りこぼしに強くなっています。

detphys_rt_advance の戻り値:

値意味渡した入力
DETPHYS_RT_ADVANCED1 tick 進めた受け付けた
DETPHYS_RT_STALLED予測の上限を超えるので相手を待つ受け付けていない（次のフレームに同じ tick の入力を渡す）
DETPHYS_RT_SYNC_WAIT相手より進みすぎているので 1 フレーム休む受け付けていない
DETPHYS_RT_DELAY_WAIT入力遅延の自動調整で入力の遅延を 1 増やした（tick は進めない）受け付けた

渡す入力は、いつも detphys_rt_next_input_tick の tick の分です。

{
    // 確定した tick（両方で同じハッシュ）: c.tick, c.hash

#遅延 0 と、入力遅延の自動調整

  • 入力の遅延（input_delay、0〜30、既定 0）を d にすると、フレームで渡した入力は「今の tick + 1 + d」の tick に入ります。d を増やすと、予測が外れてロールバックする回数は減りますが、操作が画面に出るまで d tick 遅れます。
  • 遠い相手では、遅延 0 だと待ち（STALLED）が増えます。測った例（1 プロセス 2 ピア・片道 135±15 ms・取りこぼし 20%・3600 tick）: 遅延 0 で 235 回待ち、遅延 2 で 8 回、遅延 4 で 0 回。
  • 入力遅延の自動調整（detphys_rt_set_auto_delay、既定 OFF）を ON にすると、ホストが往復時間から遅延 D を決め、「tick X から D」を両方で切り替えます。
    • 決め方: 片道 = 往復時間 / 2 ＋ 揺れ × 1（jitter_weight_milli 1000）。D = ceil(片道 / 1 tick) − rollback_ticks（既定 N/2+1 = 6）を 0〜6 に収めます。
    • 上げたい状態が 500 ms、下げたい状態が 3000 ms 続いたら切り替えます。上げる時は tick を進めずに入力だけ受け（DELAY_WAIT）、下げる時は 1 フレームで 2 tick 進めます。
    • どちらも入力を捨てないので、確定した結果は遅延によらず同じです。ゲストは、自分も ON の時だけホストの案に従います。
    • 測った例: PC と Galaxy S9 の間（片道 120〜150 ms を注入）で両方とも遅延 3 になり、待ちは 75 / 76 回 → 8 / 6 回に減りました。

#再接続（リアルタイム）

どちらのピアも接続の識別子を持ち、相手の識別子が変わったら（相手が再起動たら）、生き残った側が自分の確定 tick T の状態と T の両ピアの入力を送ります。再起動た側はそれに置き換えて T から続けます。アプリは、落ちた側で同じ設定のセッションを作り直すだけです。相手の状態に置き換えたフレームは DETPHYS_RT_FRAME_REJOIN が立つので、描画や音はそこで今の状態から作り直します。両方が同時に落ちると tick 0 からです。

#snapshot

ロールバック・再同期・再接続のために、ワールドの状態を呼び出し側のバッファに写し取ります（コアの中では画像を確保しません）。

種類中身戻せる所既定で使う所
dyn（DETPHYS_SNAPSHOT_DYNAMIC）step で変わる状態だけ。形や静的な物は、ワールドが覚えている base（full の画像）から戻す取ったワールドだけリアルタイムの snapshot のリング（N+1 個）
full（DETPHYS_SNAPSHOT_FULL）全部同じ形を同じ順で登録した別のワールドにも（x64 と arm64 の間でもそのまま）再同期・再接続で送る状態、ターン制のゲストの毎ターンの保存
  • base はコアが自動で取り直します（ボディや形を作る・消す・位置を直接決めた後の最初の dyn で）。覚えておく base は既定 4 個（snapshot_base_slots）。足りない tick は、リアルタイムの輪ではコアが自動で full に落とします。
  • ターン制は毎ターン形が増えるので、ゲストの毎ターンの保存は full が既定です（detphys_turn_set_checkpoint_kind で dyn も選べます。同じ物を動かすだけのゲームなら dyn が軽くなります）。
  • 大きさの目安（2D、凹形状の動くボディ 200 体が全部起きている時）: dyn 約 0.55〜0.7 MB・full 約 1 MB（ベイクした形では dyn 1.5 MB・full 2.1 MB）。

#凹形状とベイカー

Box2D の形は 8 頂点までの凸多角形です。DetPhys は凹形状を凸多角形の組にして、1 つのボディに全部付けます。分解は前もってベイカーで済ませ、mm の整数の頂点データ（.dnshape）として配るので、実行時に端末ごとに分解することはなく、どの端末でも同じデータになります。

形はエディタでベイクします。Unity では Window > DetPhys > Shape Baker（テクスチャかスプライトを選び、プレビューを見ながら設定を変えて保存）か、画像を右クリック > DetPhys > Bake Concave Shape です。できるのは .dnshape.bytes のアセットで、マッチコンポーネントの Shapes に入れて使います。ベイカーの流れ:

  1. 画像のアルファ（既定 128 以上が内側）から輪郭を取る（既定 128 px / m。スプライトならその Pixels Per Unit）。
  2. Douglas-Peucker で間引く（許容誤差 Simplify 既定 1 px）。Box2D が消してしまう細かい頂点（直線から 11 mm 未満）は先に消す。
  3. 凸多角形に分ける: Steiner（既定。長い直線の辺に点を足して数を減らす）か Hertel-Mehlhorn（新しい頂点を作らない）。どちらもすき間・重なりは 0 です。
  4. mm の整数にして .dnshape（v1、チェックサム付き）に書く。原点は画像の中心です。

ベイカーはネイティブのコアの中で整数だけで計算するので、同じ画像と設定ならどのマシンでも同じバイト列になります。PNG はファイルから直接読むので、テクスチャの Read/Write・圧縮・Max Size で形は変わりません。

  • 使い方: .dnshape のバイト列を、セッションの設定の meshes（登録した順に番号 0, 1, …）か detphys_world_add_mesh で登録し、形の種類 DETPHYS_SHAPE_MESH と番号で付けます。両方のピアで同じ形を同じ順に登録します。
  • 精度: 輪郭からの最大のずれ 4〜11 mm（サンプルの 8 形、128 px / m・1 px）。約 1 cm より細かい凹凸は消え、穴は埋めます。
  • 負荷は凸多角形の数にほぼ比例します。サンプルの 8 形は 1 形あたり平均 9.4 個（steiner）。許容誤差を大きくすると数が減ります（2 px で 67 個 / 8 形）。

#動く凹形状

回る歯車・往復する足場・上下する U などを、tick の関数で動くキネマティックのボディにします（detphys_kinematic.h）。

  • 動きは状態を持たないので、ロールバックしても tick から同じ値を作り直せます（snapshot の値と作り直した値はビットまで同じ）。
  • 毎 tick、関数の位置にぴったり合わせ、次の tick の位置に着く速度を与えます。Box2D はその速度で上の物を運ぶので、乗った物が滑らず、震えません。
  • 動き（detphys_motion_desc、単位は mm・mrad・mrad/s・tick の整数）:
パス動き
DETPHYS_PATH_FIXED動かない（自分の回転 spin_mrad_s だけ。回る歯車・羽根）
DETPHYS_PATH_PINGPONGA と B の間を往復（片道 period_ticks）
DETPHYS_PATH_ORBIT円を回る
DETPHYS_PATH_POINTS点をたどる（点ごとに角度も。ループか往復。同じ点を続けるとその間止まる）
DETPHYS_PATH_CALLBACKゲームのコールバックが tick から位置と角度を決める（整数だけで計算する）

どのパスにも自分の回転 spin_mrad_s と時間のずらし phase_ticks を足せます。区間の速さは既定で端が 0（DETPHYS_EASE_SMOOTH、乗った物が飛ばされにくい）。

  • 速い動き: Box2D は動くボディどうしの接触を tick の初めに 1 回探します（先読み約 2 cm）。いちばん速い点が 1 tick に subtick_move_mm（既定 20 mm）より動く tick だけ、ワールドを最大 max_subticks（既定 4）回に分けて進めます（分割）。既定のままで、小さな物（4〜15 cm）がすり抜けない速さは、いちばん速い点で歯車 34・足場 180・羽根 43・上下する U 18 m/s まででした。分割した tick は、その回数分重くなります。
  • セッションでは表をセッションに渡します（detphys_rt_create_kinematic・detphys_turn_create_rule_kinematic、Unity はルールの UsesKinematic => true）。1 tick の順番は「update → apply_inputs → 分割して進める → after_tick」で、ロールバックの再計算も同じです。
  • 3D のワールドの動く凹形状は 動く凹形状（3D） にあります（detphys3d_kinematic.h）。

#3D

3D のワールド（detphys3d.h、Box3D）も、2D と同じセッションに載せられます。考え方（tick・入力・予測・ロールバック・照合・再同期・再接続・入力遅延の自動調整）は全部同じです。

detphys_rt_config c; detphys3d_world_desc w;
detphys_rt_config_default3d(&c, &w);          // snapshot は FULL、ワールドは既定値（60 Hz・4 サブステップ・重力 −10000 mm/s²）
c.local_peer = 0;                            // ほかの設定は 2D と同じ
detphys_rt_rule3d r = { sizeof r, 3, 0 };     // 入力 3 語・状態 0 語
r.begin = my_begin;                          // 凸包の登録・床・プレイヤーを作る（detphys3d_world_* で）
r.apply_inputs = my_apply;
detphys_rt_session* s = detphys_rt_create3d(&c, &w, &r, &transport);   // ターン制は detphys_turn_create_rule3d
// 毎フレーム: 2D と同じ poll → advance → next_confirmed。描画は detphys3d_world_read_transforms(detphys_rt_world3d(s), ...)
  • 形: 箱・球・カプセル・凸包。凸包は整数の点から detphys3d_world_add_hull で作って登録し、番号で付けます（同じ中身なら同じ番号）。凸包は begin（ターン制は begin_match）の中で、両方のピアで同じ順に登録します。凸包の中身は設定の照合に入ります。
  • 向きは整数の四元数（qx, qy, qz, qw）です。大きさは自由で、コアが正規化します。エンジンの float の四元数は DETPHYS3D_QUAT_ONE（2^30）倍して丸めて渡します。三角関数を使いません。
  • snapshot は full が既定です（3D では dyn にしても 6〜9% しか小さくならないため）。
  • 送る状態（再同期・再接続）は transfer（detphys3d_world_transfer_*）で、full の画像に形の登録簿の中身と凸包の表を足したものです。登録簿の並びが違っていても、受け取った側が作り直してから戻します。115 体で 190〜260 KB です。
  • ワーカーは 1〜32 本（既定 1）、プールはコアの自前（既定。Android で Box3D 内蔵より速かった）・Box3D 内蔵・エンジンのジョブから選べます。本数を変えてもハッシュは変わりません。
  • desync デバッガーも 2D と同じ設定で ON にできます。報告のフィールドは 3D のフィールド（x y z・qx〜qw・vx vy vz・wx〜wz）です（5. desync への対処）。
  • まだ無いもの: ジョイント・センサー・接触のイベント・レイの問い合わせ。エンジンごとに使える 3D の範囲は 1. 概要 にあります。

Godot では、3D のルールを GDScript でも書けます。DetPhysRtRule3D（ターン制は DetPhysTurnRule3D）を継いでコールバックを書き、DetPhysRtSession.create3d（DetPhysTurnSession.create3d）に渡します。ワールドに渡す値は整数の Dictionary です（7. API リファレンス の Godot の節）。

extends DetPhysRtRule3D   # 2 人が球を転がすだけのルール

func _init() -> void:
	input_words = 2          # [x -100〜100, z -100〜100]
	state_words = 0
	rule_id = 0x42414C4C00000001
	params = PackedInt32Array([300])   # 球の半径 mm

func _begin(c: DetPhysRtContext3D) -> void:
	var w := c.world
	w.add_body({"type": DetPhysRuleWorld3D.DETPHYS3D_BODY_STATIC, "y_mm": -500,
		"shape": {"kind": DetPhysRuleWorld3D.DETPHYS3D_SHAPE_BOX, "half_x_mm": 8000, "half_y_mm": 500, "half_z_mm": 8000}})
	for p in 2:
		w.add_body({"x_mm": -3000 + 6000 * p, "y_mm": params[0],
			"shape": {"kind": DetPhysRuleWorld3D.DETPHYS3D_SHAPE_SPHERE, "radius_mm": params[0]}})

func _apply_inputs(c: DetPhysRtContext3D, inputs: PackedInt32Array) -> void:
	for p in 2:
		c.world.apply_force(1 + p, inputs[p * 2] * 2000, 0, inputs[p * 2 + 1] * 2000)

#動く凹形状（3D）

3D でも、回る歯車・回転台・止まりながら往復する足場・リフト・円を回る足場・ゆれる足場を、tick の関数で動くキネマティックのボディにできます（detphys3d_kinematic.h、バージョン 1）。考え方は 2D の動く凹形状と同じです。動きは状態を持たないので、ロールバックしても tick から同じ値を作り直します。毎 tick、関数の姿勢にぴったり合わせ、次の tick の姿勢に着く速度・角速度を与えます。速い tick だけ分割して進めます。

  • 動き（detphys3d_motion_desc、単位は mm・mrad・mrad/s・tick の整数、向きは整数の四元数）:
パス動き
DETPHYS3D_PATH_FIXED動かない（回転軸のまわりの回転 spin_mrad_s だけ。回る歯車・回転台）
DETPHYS3D_PATH_PINGPONGA と B の間を往復（片道 period_ticks）。A で hold_a_ticks・B で hold_b_ticks だけ止まる。上下に動かせばリフト
DETPHYS3D_PATH_ORBIT中心のまわりを、回転軸のまわりに orbit_mrad_s で回る。向きは spin だけで決まる（spin 0 なら向きを変えずに円を描く）
DETPHYS3D_PATH_POINTS点をたどる（点ごとに回転軸のまわりの角度も。ループか往復。同じ点を続けるとその間止まる。止まる階が 3 つ以上のリフトなど）
DETPHYS3D_PATH_CALLBACKゲームのコールバックが tick から位置 [µm] と整数の四元数を決める（整数だけで計算する）
  • 向きは、初めの向き（qx〜qw）を回転軸（axis_x〜axis_z。0, 0, 0 = y 軸）のまわりに a(t) だけ回したものです。a(t) は spin × 時間で、POINTS は点の角度も足します。
  • CALLBACK 以外のパスには、spin と時間のずらし phase_ticks を足せます。区間の端は既定で速さ 0 です（DETPHYS_EASE_SMOOTH）。
  • 形は detphys3d_kinematic_add で最初の形を付け、detphys3d_world_add_shape で凸包・箱を足して凸の組にします。近似はしません。
  • 速い回転でも、tick の終わりに関数の向きに着きます。Box3D の角速度の上限を外し、角速度を Box3D の積分に合わせて補正しているためです（40 rad/s・120 tick で差 2.0e-6 rad）。
  • 分割は 2D と同じ設定です（subtick_move_mm 20 mm・max_subticks 4）。いちばん速い点は外接半径で数えるので、外周に壁を付けた大きな回転台ほど分割が増えます。
  • セッションには、表を detphys_rt_create3d_kinematic・detphys_turn_create_rule3d_kinematic で渡し、ルールの begin（begin_match）の中で add / bind します。表の中身は設定の照合に入ります。
  • ターン制では、動いているキネマティックがあるとワールドが落ち着かないので、after_tick で tick 数などでターンを終えます（4. 決定論を守るためのルール の 12）。
  • 確かめたこと: 回る凹の歯車と、往復・リフト・円・ゆれる足場のシーン（各 900 tick）で、PC の 5 つのビルドと Galaxy S9 の全 tick が一致し、すり抜けは 0 でした。止まった足場の上の物は震えません。
  • 負荷は 6. パフォーマンス にあります。

#回る台の上の物は外へ滑る

3D で回るキネマティック（歯車・回転台）に載せた物は、摩擦が足りていても外へゆっくり滑ります（0.3 rad/s の台で 10 秒に約 0.2 m）。Box3D の接触の解き方による性質で、どの端末でも同じように滑るので決定論は壊れません。

  • 物を載せたまま回す台には、縁や仕切りを付けます。
  • プレイヤーが乗る台では、移動の処理（ルールの apply_inputs）でその場所の台の速度（角速度 × 軸からの距離）を足します。
  • 往復する足場・リフト・向きを変えずに円を回る足場は、この影響を受けません。

#トランスポート

  • セッションは、データグラム（1 つ最大 1200 バイト）を運ぶトランスポートのインターフェース（detphys_transport の send・recv の 2 つの関数）だけを使います。届かない・順番が入れ替わる・重なることがあってよく、セッションが再送と並べ直しで埋めます。Steam・EOS・自前のリレーは、このインターフェースに差し込みます。
  • DetPhys に入っているトランスポート:
    • UDP（detphys_udp.h、IPv4、LAN・テスト用）: 待ち受け（LISTEN、最後に届いた送り主に返す）か、つなぐ（CONNECT）。どちらがホストでもよく、ファイアウォールのある端末はつなぐ側にします。
    • ループバック（detphys_loopback_*）: 1 プロセスの中で 2 ピア。遅れ・順番の入れ替え・取りこぼし・重なりを seed 付きで入れられます（テスト用）。
    • Unity の DetPhysFaultyLink・Godot の DetPhysLink.set_faults: UDP やループバックに、壁時計の ms で遅れ・揺れ・取りこぼし・重なりを足すテスト用のトランスポート。
  • 接続のインターフェース（detphys_link.h）: トランスポートのインターフェースの上に「ルームを作る（ホスト）・6 桁のルームコードで入る（ゲスト）・毎フレームの poll・状態と理由」をそろえた層。UDP・ループバック・1 プロセスでルームの流れを試すテスト用のロビーが入っていて、EOS・Steam・自前のリレーも同じインターフェースに載せます。詳しくは 8. トランスポートとルームコード。
  • ネット越し: 入っている UDP は IP を直接打つ LAN 用で、NAT やモバイル回線（CGNAT）は越えられません。ネット越しは、EOS P2P（EOS P2P）か、自分のサーバーに置くリレー（8. トランスポートとルームコード）か、自分のトランスポートを detphys_transport に差し込んで使います。
  • 時計: 実際のネットワークでは、エンジンの単調な時計（マイクロ秒）を渡します（detphys_turn_poll_at・detphys_rt_poll / advance）。時計は再送・tick の進め方だけに使い、ハッシュには入りません。

#ワーカー（スレッド）

worker_count（1〜64、既定 1）で step を手伝うスレッドの数を決めます。本数・プールの種類を変えてもハッシュは変わりません（ピアごとに違ってもよい）。凹形状の動くボディが 200 体ほどあると 4 本で step が速くなりますが、単純な形が少ない時は 1 本の方が速いことがあります。プールはコアの自前（既定）・Box2D 内蔵・エンジンのジョブ（enqueue_task / finish_task）から選べます。
