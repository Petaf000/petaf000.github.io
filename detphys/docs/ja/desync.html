desync への対処（desync デバッガー）

症状から選ぶ

  1. つながらない相手待ちのまま進まない。設定・ルール・形が相手と違う
  2. ずれたと出た試合は自動で直って続く。原因を知りたい
  3. 報告を読みたいどの tick・ボディ・フィールド・何 ULP か、原因は何か
  4. テスターから記録をもらうバンドル（.dndb）にしてファイルで受け取り、手元で比べ直す

#desync は自動で直る

2 つのピアの状態がずれると、ハッシュの照合で見つかります（リアルタイムは確定した tick ごと・ターン制はターンの終わりごと）。見つけたら、ホスト（ピア 0）の状態をゲストに送って置き換えるので（再同期）、試合はそのまま続きます。

  • リアルタイム: detphys_rt_frame.flags に DETPHYS_RT_FRAME_DESYNC（見つけた）・DETPHYS_RT_FRAME_RESYNCED（ゲストが置き換えた）が立ちます。数は detphys_rt_get_stats の hashes_mismatched・desyncs・resyncs。
  • ターン制: そのターンの報告の flags に DETPHYS_TURN_FLAG_DESYNC・DETPHYS_TURN_FLAG_RESYNCED が立ちます。

ずれは「どこかで決まり（4. 決定論を守るためのルール）が破れている」しるしです。desync デバッガーは、その場所を一度で示します。（そもそも相手とつながらない時は、desync より前の問題です。つながらない時 を見てください。）

#desync デバッガーを ON にする

既定は OFF です。OFF の時は何も記録せず、何も送りません（通信のバイト列・1 フレームの時間・ハッシュは、ON にしない時と同じです）。

detphys_debug_session_config dbg;
detphys_debug_session_config_default(&dbg);
dbg.enabled = 1;                 // 両方のピアで ON にする
dbg.ticks_before = 30;           // 交換する範囲: desync した tick T の 30 tick 前から T まで（既定）
detphys_rt_set_debug(session, &dbg);      // ターン制は detphys_turn_set_debug(session, &dbg)
設定（detphys_debug_session_config）既定中身
enabled01 = 記録して、desync したら交換する
flagsDETPHYS_DEBUG_REC_DEFAULTBox2D の深いハッシュ（REC_BOX2D_HASH。3D は Box3D の状態のハッシュ）とボディの種類・形・タグ（REC_META）も記録する。外すと記録の負荷が約半分
ticks_before30desync した tick T の何 tick 前から交換するか
ring_ticks0（自動）記録の輪の長さ。自動なら、リアルタイムは ticks_before + 予測の上限 + 1 + 2 秒分、ターン制は ticks_before + 1 ターンの上限 + 2
max_bodies0（自動）1 tick に記録できるボディの数。足りなくなったら倍にして作り直す（それまでの記録は消える）
max_reports4交換する回数の上限（超えたずれは数えるだけ）
timeout_ms10000相手の記録を待つ時間（相手が OFF だとここで FAILED）
scene_id / label0 / 空記録に付ける印（0 = セッションの設定のハッシュ、空 = "host" / "guest"）
  • 両方のピアで ON にします。 相手が OFF だと相手の記録が届かず、timeout_ms で FAILED になります。
  • いつ呼んでもかまいません（tick 0 で呼べば、作った直後の状態から記録します）。
  • エンジンの層: Unreal はセッションの SetDebug・GetDesyncReportCount・GetDesyncReport（Blueprint からも。FDetPhysDebugSettings・FDetPhysDesyncReport）で使えます。Unity はセッションの SetDebug・TryGetDebugReport・DebugBundle、Godot はリアルタイムのセッションの set_debug・get_debug_report・get_debug_bundle で使えます（7. API リファレンス）。
  • 3D: 3D のセッション（detphys_rt_create3d・detphys_turn_create_rule3d）でも、同じ設定で detphys_rt_set_debug / detphys_turn_set_debug を ON にできます（detphys_debug_abi_version() が 3 以上のコア）。違う所（フィールド・深いハッシュの意味・記録の形）は 3D のワールドとセッション にあります。

#desync が起きた時の流れ

  1. 照合で desync を見つけると、ホストが desync した tick T と範囲 [T − ticks_before, T] を決めます（前の再同期の tick より後だけ）。
  2. 両方のピアが、自分の記録（リアルタイムは確定した tick だけ）を相手に小分けにして送ります。遊びの通信を長く止めないよう、少しずつ送ります。再同期はいつもどおり同時に行います。
  3. 両方そろうと、どちらのピアでも A = ホスト・B = ゲストで比べ、同じ報告を持ちます。そのフレームに DETPHYS_RT_FRAME_DEBUG（ターン制はそのターンの報告に DETPHYS_TURN_FLAG_DEBUG）が出ます。PC と Galaxy S9 の間で、見つけてから報告まで約 0.3 秒でした（3D は 1 プロセスの 2 ピア・片道 20〜40 ms・取りこぼし 5% で 0.4〜0.6 秒）。
  4. つなぎ直し・再起動があると、途中の交換は FAILED（DETPHYS_DEBUG_FAIL_LINK）になります。

#報告の読み方

uint32_t n = detphys_rt_debug_count(session);           // 報告の数（WAITING を含む）
detphys_debug_session_report rep = { sizeof rep };
detphys_debug_diff diffs[16];
detphys_rt_debug_get(session, n - 1, &rep, diffs, 16, NULL, 0);
if (rep.status == DETPHYS_DEBUG_EXCHANGE_READY) {
    // rep.report.cause / first_tick, rep.first_diff.body / field / a / b / ulp
}
  • status: WAITING（交換の途中）/ READY（報告ができた）/ FAILED（fail_reason: TIMEOUT・LINK・RECORD・COMPARE）。
  • report.first_tick: 最初に何かが desync した tick。input_first_tick・state_first_tick・body_first_tick・box2d_first_tick・hash_first_tick で、どれが最初にずれたか分かります（ずれていなければ DETPHYS_DEBUG_NONE）。
  • first_diff: いちばん先に違ったボディの ID・フィールド（x y cos sin vx vy w など。3D は x y z qx〜qw vx vy vz wx〜wz）・両方の値の生のビット・ULP の差。
  • report.diff_bodies・diff_values: その tick で違ったボディとフィールドの数。spread を渡すと、tick ごとに「違ったボディの数」が入り、desync が広がる様子が見えます。

#原因（report.cause）と、疑う所

原因名前意味疑う所
DETPHYS_DEBUG_CAUSE_INPUTinput入力が違う（物理より前）入力の受け渡し・量子化をどこでしたか（受け取った側でもう一度量子化していないか）・ボタンの取りこぼし
DETPHYS_DEBUG_CAUSE_STATEstate入力も物理も同じで、ゲームの状態ワードが違うルールのコード（乱数・順番・時計・ルールのオブジェクトに置いた値。4. 決定論を守るためのルール の 5〜8）
DETPHYS_DEBUG_CAUSE_SETUPsetupボディの数・種類・形・タグが違う作り方・消し方（作る順番・条件・形の登録の順番）。tick 0 からなら、初めの作り方
DETPHYS_DEBUG_CAUSE_PHYSICSphysics同じ入力・同じ形で、物理の値がずれたルールの float の計算・ビルド設定（fast-math・FMA）・自分でビルドしたコア
DETPHYS_DEBUG_CAUSE_HIDDENhidden見える値は同じで、Box2D の深いハッシュ（3D は Box3D の状態のハッシュ）だけ違う接触などの隠れた状態。次の tick から値に出ます。物理と同じ所を疑う
DETPHYS_DEBUG_SAME / NO_OVERLAPsame / no_overlap全部同じ / 共通の tick が無い範囲（ticks_before）を広げる

例: 片方を fast-math でビルドしたピアと対戦すると、両方の報告が「tick 0・ボディ 1・x・1 ULP・physics」を示しました（mm → m の ÷1000 が ×0.001 に変わったため）。

#記録をファイルにする（バンドル）

uint32_t size = 0;
detphys_rt_debug_bundle(session, index, NULL, 0, &size);       // DETPHYS_ERR_CAPACITY で大きさが返る
void* buf = malloc(size);
detphys_rt_debug_bundle(session, index, buf, size, &size);
detphys_debug_write_file("desync_0.dndb", buf, size);          // パスは UTF-8（Windows でも日本語のパスでよい）

バンドル（DNDB）には、2 つのピアの記録（DNDR）と報告が入っています。WAITING・FAILED でも、届いている記録だけで作れます。テスターから送ってもらうのに便利です。

#記録を比べ直す

テスターから受け取ったバンドル（か 2 つの記録）を手元で読み直す時は、コードで 2 つの記録を比べます。

  • C: detphys_debug_bundle_info_get で、バンドルの中のホストとゲストの記録の場所が分かります。detphys_debug_compare で 2 つの記録を比べます。detphys_debug_file_info_get で記録の見出しと tick の範囲を読めます。
  • Unity（C#）: DetPhysDebug.Compare(a, b)（A が基準。たとえばホスト）は、報告と同じ項目（最初にずれた tick・ボディ・フィールド・両方の値・ULP の差・原因）を持つ DetPhysDebugComparison を返します。DetPhysDebug.TryGetFileInfo で記録の見出しを読めます。
  • 結果の読み方は報告と同じです（報告の読み方・原因の表）。
  • desync のことでサポートに問い合わせる時は、バンドルのファイル（.dndb）を添えてください。
  • 3D の記録とバンドルも同じように比べられます（3D のワールドとセッション）。

#セッションを使わずに記録する

自分で tick を回す時は、記録の部品を直接使えます（detphys_debug.h）: detphys_debug_recorder_size → 呼び出し側でバッファを確保 → detphys_debug_recorder_init → tick ごとに detphys_debug_record(rec, world, 入力, 状態) →detphys_debug_export で DNDR のバイト列にする → detphys_debug_compare（Unity は DetPhysDebug.Compare）で比べる。記録はワールドを読むだけで、ハッシュを変えません。ロールバックで同じ tick をもう一度記録すると、その tick から後を捨てて書き直します。

#3D のワールドとセッション

3D のワールド（detphys3d.h）でも、記録・交換・報告・バンドルは 2D と同じ流れです。3D のセッションで ON にできるかは detphys_debug_abi_version() >= 3 で見分けます（rt・ターン制のバージョンは変わっていません）。違う所:

  • フィールド: 3D のボディは 13 フィールドです。位置 x y z・向き（四元数）qx qy qz qw・速度 vx vy vz・角速度 wx wy wz。DETPHYS_DEBUG_FIELD_X・Y・VX・VY は 2D と同じ番号で、Z〜WZ は 12〜20 です（cos sin w は使いません）。報告の first_diff.field もこの名前です。
  • 深いハッシュ: 3D では、box2d_hash・box2d_first_tick・DETPHYS_DEBUG_REC_BOX2D_HASH の中身は Box3D の状態のハッシュ（detphys3d_world_engine_hash と同じ値）です。名前は 2D と同じにしてあります。原因 hidden も「Box3D のハッシュだけ違う」と読みます。
  • ハッシュ: 記録の hash は detphys3d_world_hash（照合に使うもの）と同じ値です。
  • 種類と形: ボディの種類は DETPHYS3D_BODY_*、形は box・sphere・capsule・hull（DETPHYS3D_SHAPE_*）で、2D でメッシュの番号を入れる所（detphys_debug_diff.mesh）には凸包の番号が入ります。
  • 記録の形: 3D の記録は形式のバージョン 2（DNDR）で、detphys_debug_file_info.flags に DETPHYS_DEBUG_FILE_3D が立ちます。2D の記録は今も形式 1 のままです。2D と 3D の記録を比べると DETPHYS_ERR_FORMAT です。
  • 大きさ: リアルタイムの 3D（約 115 体、PC）で 1 tick 約 7.5 KB、交換した記録は 1 ピア 166〜222 KB（31 tick）でした。ターン制の 3D（最大 12 体）は 384 バイト / tick です。
  • 例: 片方を fast-math でビルドしたコアの 3D の記録を基準の記録と比べると、2D と同じく「tick 0・ボディ 1（箱）・x・1 ULP」を示しました。
  • 3D の記録は、ビルド（msvc・clang-cl・mingw・debug）によらず同じバイト列で、Galaxy S9（android-arm64）で書いた記録も PC の基準の記録と同じでした（61 tick・ずれ 0）。
  • 2 プロセスの 3D の対戦（UDP、3D の押し合い 約 70 体〔箱 40・球 8・凸包 12 など〕、600 tick・60 Hz、片道 20〜40 ms・取りこぼし 5%・重なり 1% を注入し、ゲストの値を tick 150 と 400 でわざと 1 ULP ずらす）: PC の中の 2 プロセス、PC ↔ S9（S9 がゲスト・S9 がホストの両向き。Wi-Fi の UDP）のどれでも、両プロセスの報告が同じで、2 つのずれ（tick 150・ボディ 68・x・1 ULP、tick 400・ボディ 76・x・1 ULP）を 1 回で示しました。ずらした区間の外では、確定 tick のハッシュが 600 tick 全部一致しました。
  • 片方を fast-math でビルドしたコアとの 2 プロセスでも、両方の最初の報告が「tick 0・ボディ 1・x・1 ULP」でした（凸包の無いシーン。下の注意）。
  • 負荷（上の表）: S9 では記録が 1 tick 約 175 µs と、PC（15〜19 µs）より重くなります。PC ↔ S9 で S9 の 1 フレームの p99 は、OFF の 7.1〜9.3 ms から ON で 8.9〜10.6 ms になりました（S9 は大きいコアに固定せず、壁時計の 60 Hz で測った値）。通信量は 1 tick 34〜39 B から 497〜795 B に増えますが、これは desync した時の記録の交換（約 30 万 B）を含む値で、ずれなければ交換はありません。
  • 注意: 3D のセッションは凸包の中身（チェックサム）を設定の照合に入れます。凸包の計算が違うビルド（fast-math など）の相手とはつながらず、両方に「shapes・最初に違う形 0」と出ます（つながらない時）。

#セッションを使わずに 3D を記録する

記録の設定の dimensions を 3 にして記録を作り（detphys_debug_config_default の後に cfg.dimensions = 3）、tick ごとに detphys_debug_record3d(rec, world3d, 入力, 状態) を呼びます。あとは 2D と同じく detphys_debug_export → detphys_debug_compare です。ボディを読む時は detphys_debug_file_bodies3d（detphys_debug_body3d: 生のビット 13 個・凸包の番号）を使います。2D と 3D の API を取り違えると、記録する時は DETPHYS_ERR_ARGUMENT、読む時は DETPHYS_ERR_FORMAT です。

#動く凹形状がある時

detphys_kinematic_check で、ワールドの中のキネマティックのボディが、動きの関数から作り直した値とビットまで同じかを確かめられます（0 = 全部同じ）。ロールバックの後に 0 でなければ、動きのコールバックが tick 以外のもの（時計・ゲームの外の変数）に頼っています。3D の表は detphys3d_kinematic_check で同じように確かめます（位置・向き・速度・角速度の生のビット）。3D のセッションでは、表の中身（付けた動き・分割の設定）が違うピアとはつながりません（設定の照合に入るため）。表の中身は記録・報告には出ません。つながらない時は、detphys_tag_info の diff_parts に kinematic が出ます（つながらない時）。

#つながらない時（設定の照合が合わない）

同じ LAN・同じポートなのに相手待ちのまま進まない（rt は DETPHYS_RT_FRAME_CONNECTED が立たない・ターン制は CONNECTING のまま）時は、まず決定論より前に、2 つのピアが「同じものを動かしていない」ことを疑います。ピアは、つなぐ前に照合のタグ（設定・ルール・形・凸包・キネマティックの表・コアのバージョンから作る値。rt は設定の照合の値、ターン制は設定のハッシュ）を比べ、タグが違う相手のパケットは捨てます。違うものを動かしたまま対戦すると、tick 0 からずれるためです。rt バージョン 7・turn バージョン 9 のコアは、タグが合わないパケットを受け取ると数えて、相手とタグの中身（部分ごとのハッシュ）を送り合うので、どの部分が違うかが両方のピアで分かります。両方が新しいバージョンなら、ふつうは最初のパケットから往復 1〜2 回（数十 ms）です。

detphys_tag_info ti = { sizeof ti };
detphys_rt_get_tag_info(session, &ti);                  // ターン制は detphys_turn_get_tag_info。毎フレーム読んでよい
if (ti.flags & DETPHYS_TAG_INFO_ACTIVE) {               // タグが違う相手から来ていて、タグが合う相手からはまだ何も届いていない
    if (ti.flags & DETPHYS_TAG_INFO_REMOTE_KNOWN) {     // 相手の中身が届いた = どこが違うか分かる
        for (uint32_t p = 1; p < (1u << DETPHYS_TAG_PART_COUNT); p <<= 1)
            if (ti.diff_parts & p) printf("相手と設定が違う: %s\n", detphys_tag_part_name(p));
        if (ti.diff_parts & DETPHYS_TAG_PART_SHAPES) printf("最初に違う形: %d\n", ti.first_shape_diff);
    } else {
        printf("相手と設定が違う（どこが違うかは不明。相手のコアが古いかもしれない）\n");
    }
}
  • 印: rt は detphys_rt_frame.flags に DETPHYS_RT_FRAME_TAG_MISMATCH が立ちます（タグが合う相手からまだ何も届いていない間と、その呼び出しの間にタグが合わないパケットが届いた時）。ターン制は detphys_tag_info.flags の DETPHYS_TAG_INFO_ACTIVE を見ます。フィールドの意味は 7. API リファレンス にあります。
  • セッションの振る舞い: rt のセッションは待ち続けます（あきらめません。やめるかはアプリが決めます）。ターン制は、設定のハッシュが違う HELLO / WELCOME を受けると今までどおり ERROR になり、相手の中身が届くと detphys_turn_error の文の後ろに「（違う所: shapes (first shape 0)）」のように違う部分が足されます。
  • エンジンの層とサンプル: 同じ中身を、Unity は TryGetTagInfo、Godot は get_tag_info() とシグナル tag_mismatch、Unreal は GetTagInfo で読めます（7. API リファレンス）。サンプルは、つながる前に ACTIVE を見たら相手の中身を待ち、「相手と設定が違います（違う所: rule）」と出して接続をやめます。やめるかどうかはゲームが決めます（コアは知らせるだけです）。
  • session_id だけ違う相手（ターン制）: ERROR にせず、数えて知らせ（違う所は config）、待ち続けます。同じポートに別の試合の古いパケットが紛れても、今の試合を壊さないためです。
  • 古いコアが相手: rt バージョン 6・turn バージョン 8 までのコアはタグの中身を送らないので、どこが違うかは分かりません。REMOTE_KNOWN が立たないまま ACTIVE が続くなら、相手のコアのバージョンを疑います。
  • REMOTE_KNOWN なのに diff_parts が 0: 部分のハッシュは全部同じで、タグの全体だけが違います（32 bit に畳んだ部分のハッシュがぶつかった時だけで、まず起きません）。
違う所何が違うか直し方
versionコアの照合・通信のバージョン、または 2D と 3D両方を同じバージョンのコア（同じバージョンのパッケージ・プラグイン・APK）で作り直す。2D と 3D のセッションどうしはつながりません
configsession_id・tick の速さ・サブステップ・重力・3D の接触の調整・ターン制の最初の手番と 1 ターンの tick の上限両方で同じ設定を渡す。session_id は試合ごとに両方で同じ値にする
rulerule_id・入力と状態ワード数・params（組み込みの押し合いの箱の数などの設定も params）両方で同じルール・同じバージョンのルールのコード・同じ設定（サンプルどうしなら同じサンプル・同じ動くステージ）
shapes2D: 登録した形（.dnshape）の中身・数・順番 / 3D: 凸包の中身（checksum）と頂点数・数・順番2D は同じ .dnshape を同じ順に登録する。3D で形のデータが同じなのに違うなら、凸包を作る計算が違うビルド（fast-math・FMA・自分でビルドしたコア）を疑う（4. 決定論を守るためのルール）。first_shape_diff が最初に違う形の番号
kinematicキネマティックの表（渡したか・flags・付けた動き・分割の設定）両方で同じ表（同じ動きを同じ順に・同じ分割の設定）を渡す

測った例（PC の中の 2 プロセス、UDP、遅れ 20〜40 ms・取りこぼし 5%）: 2D の rt でゲストだけ押し合いの箱の数を変える（rule）・3D の rt でゲストだけ凸包 0 を 1 mm ずらす（shapes・形 0）・ターン制で 1 ターンの tick の上限を変える（config。両方が ERROR で、文に「違う所: config」）・ターン制で session_id だけ変える（config。ERROR にならない）のどれでも、両方のプロセスが開始から 0.1 秒以内に違う所を知りました（中身を送ったのは片側 1〜2 回）。1 プロセスのループバック（片道 10 ms）では、両方のピアが 30〜31 ms（片道 3 回分）で知りました。
