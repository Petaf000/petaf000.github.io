トランスポートとルームコード

セッション（ターン制・リアルタイム）は、データグラムを運ぶトランスポートのインターフェースだけを使います。この章は、その API の上で「相手を見つけてつなぐ」ための層（detphys_link.h）と、ネット越しの対戦で使うルームコードの考え方をまとめます。

  • DetPhys は サーバーの運営をしません。ルームの検索・NAT 越え・中継（リレー）は、差し込むトランスポート（EOS・Steam・自分で置くリレー）の側が持ちます。
  • トランスポートはシミュレーションの結果に入りません。ルームコード・時刻・アドレス・経路（直接かリレーか）が違っても、確定した tick のハッシュは同じです。

#2 つの層

層ヘッダー中身
データグラムのインターフェースdetphys_turn.h の detphys_transportsend・recv の 2 つの関数。1 つ最大 1200 バイト。届かない・入れ替わる・重なることがあってよい（セッションが再送と並べ直しで埋める）
接続のインターフェースdetphys_link.h（バージョン 1）ルームを作る・ルームコードで入る・毎フレームの poll・状態と理由・数え上げ。中から detphys_transport を取り出してセッションに渡す

detphys_transport を自分で作って渡すやり方は今までどおり使えます。detphys_link は、どのトランスポートでも同じ手順と同じ画面（「ルームを作る」「コードを打つ」「つながった」「相手が出た」）で書けるようにするためのものです。

#使い方（どのトランスポートでも同じ）

detphys_link* link = NULL;
/* 1. 作る（ここはテスト用のロビー。EOS などは作る関数だけが違う） */
detphys_link_create_hub(hub, &link);

/* 2. ホストはルームを作る / ゲストはルームコードで入る */
detphys_link_room_desc room;
detphys_link_room_desc_default(&room);
room.bucket = "mygame/1.2";            /* ゲームとバージョン。同じ bucket のルームだけを探す */
if (is_host) {
    detphys_link_host(link, &room);      /* ルームコードは作られる（info.room_code で読める） */
} else {
    room.code = typed_text;             /* 打った文字そのまま（全角・区切りは読み飛ばす） */
    int32_t rc = detphys_link_join(link, &room);
    if (rc == DETPHYS_LINK_E_CODE_CHECK) { /* 打ち間違い。通信の前に分かる */ }
}

/* 3. 毎フレーム poll。役が決まったらセッションを作る */
detphys_link_poll(link);
detphys_link_info info = { sizeof info };
detphys_link_get_info(link, &info);
if (!session && info.role != DETPHYS_LINK_ROLE_UNKNOWN) {
    detphys_transport tr;
    detphys_link_transport(link, &tr);
    cfg.local_peer = info.role;         /* ホスト = 0、ゲスト = 1 */
    session = detphys_rt_create_push(&cfg, &push, &tr);
}

/* 4. 終わり: セッション → link の順に壊す（link を壊すとルームを出る） */
  • 役の決め方: ルームを作った側がホスト（ピア 0 = desync の時の基準）、入った側がゲスト（ピア 1）。今のサンプルの決め方と同じです。
  • 相手につながる前に送ったものは DETPHYS_LINK_E_NOT_READY で断られます。セッションは後で送り直すので、役が決まった時点でセッションを作ってかまいません。
  • スレッド: 1 つの detphys_link は 1 つのスレッドから使います（poll・send・recv を同じスレッドで）。SDK のコールバックは detphys_link_poll の中で回ります。

#状態と理由

状態（DETPHYS_LINK_STATE_*）意味画面の例
IDLE作っただけ（ルームのあるトランスポートで、host / join の前）「ルームを作る」「コードを打つ」
OPENINGログイン・ルームを作る・探す・入る・相手への経路を作る、の途中「つないでいます…」
WAITINGホスト: ルームができて相手を待っている。UDP の待ち受け: 最初のデータグラムを待っている「ルームコード 123 456 を相手に伝えてください」
CONNECTED相手が決まり、運べる対戦の画面へ
CLOSED閉じた（理由 PEER_LEFT = 相手が出た、CLOSED = 自分で閉じた）「相手がルームを出ました」
FAILED失敗した（理由は下の表、説明は detphys_link_error）理由ごとの文

理由（DETPHYS_LINK_REASON_*）: NOT_FOUND（そのルームコードのルームが無い）・FULL（埋まっている）・CODE_TAKEN（作ろうとしたコードが使われている。API が作ったコードなら自動で作り直す）・PEER_LEFT・CLOSED・TIMEOUT・LOGIN（EOS などへのログインの失敗）・NETWORK・BACKEND（その他。detphys_link_error に説明）。detphys_link_state_name・detphys_link_reason_name は英数字の名前（"not_found" など）を返すので、エンジン側の翻訳の鍵に使えます。コアの説明の文（detphys_link_error）は作り手向けです。

#ルームコード

  • 6 桁の数字です。前の 5 桁がルームの番号（10 万通り）、最後の 1 桁がチェックディジット（Damm の方法）。
  • 1 桁の打ち間違いと、隣どうしの入れ替えは全部、通信の前に detphys_link_join が DETPHYS_LINK_E_CODE_CHECK で返します（よそのルームに入りません）。前の 5 桁の 10 万通り全部で、1 桁の誤り 5,400,000 通り・隣の入れ替え 450,000 通りを全部見つけることを確かめています。1 つ飛ばしの入れ替え（abc → cba）と同じ 2 桁の誤り（aa → bb）も約 90% 見つけます。
  • 打った文字の全角の数字・空白・ハイフン・「ー」は読み飛ばします（「１２３ー４５６」も「123 456」も同じ）。それ以外の文字があるか、数字が 6 つでなければ DETPHYS_LINK_E_CODE_FORMAT。確かめるだけなら detphys_room_code_parse。
  • 画面には 3 桁ずつ空けて（「123 456」）出すのがおすすめです。
  • ルームは bucket（ゲームとバージョンの名前。英数字と . _ - / : の 1〜63 文字）ごとに分かれます。バージョンが違うと設定の照合でつながらないので、bucket にバージョンを入れておくと、違うバージョンの人のルームは最初から見つかりません。
  • コードはホストの API が作ります（OS の乱数。detphys_link_room_desc.entropy を入れると決まったコードになる。テスト用）。決まったコードを使う時は room.code に入れます。作ったコードが使われていた時は、API が別のコードで作り直します（8 回まで。detphys_link_info.host_attempts）。
  • ルームコードはシミュレーションの結果に入りません（通信の都合だけ）。

テスト用のロビーの設定（detphys_link_hub_desc）: ルームの操作にかかる時間（op_delay、pump の回数）・ルームの数の上限・見せる経路（path。リレーの表示の試験に）・1 つのデータグラムの上限（max_packet。EOS と同じ上限で試す時に）・ルームごとの遅れ・取りこぼし・重なり（packets）。時間は detphys_link_hub_pump の回数で進みます。

#実測値（PC i7-12700F、2026-11-11）

  • いちばん大きいデータグラムは、入力と照合だけなら 55 B です。再同期の状態のかけらは rt 1051 B・ターン制 1057 B（chunk_bytes 1024 の時）。
  • テスト用のロビー（データグラムの上限 1170 B、片道 40〜80・取りこぼし 10%・重なり 2%）を通した押し合い 1800 tick と積み上げ 120 ターンで、確定 tick のハッシュが基準と全部一致しました。Galaxy S9 でも同じです。
  • UDP の API とループバックのインターフェースで同じ押し合いを回すと、確定 tick のハッシュは 2 つのトランスポート・2 つのピアで全部同じです。

#自分のトランスポートを書く（自社のサーバーなど）

detphys_link_vtable を埋めて detphys_link_create に渡します。API（detphys_link）が、大きすぎるものを断る・送った / 受け取った数を数える・ルームコードを確かめて正規化する・使われていたコードを作り直す、を受け持つので、実装は運ぶこととルームの操作だけを書けば済みます。

関数要る？すること
send / recv要る1 つ送る（0 = 受け付けた、負 = 送れない）／ 1 つ取り出す（大きさ、無ければ 0）
get_info要る状態・役・経路・理由・往復時間（知らなければ -1）・相手と自分の説明・ルームコードを書く（数え上げは API が書く）
poll任意毎フレーム。SDK を回す
host / join任意（無ければ DETPHYS_LINK_E_UNSUPPORTED）ルームを作る／入る。コードは API が確かめた 6 桁で来る。すぐ終わらなくてよい（OPENING にして poll の中で進める）
wait・error・close・destroy任意待つ（ヘッドレスのテスト用）・説明の文・ルームを出る・片付け

決まり:

  • max_packet（1 つのデータグラムの最大）を正しく書く。セッションが送るいちばん大きいものは、再同期の状態のかけら（chunk_bytes + 見出し 約 33 B）です。chunk_bytes は 64〜1100（既定 1024）なので、トランスポートの上限より 40 B 以上小さくしておけば収まります。
  • 信頼性なし・順番なしで運んでかまいません（セッションが埋めます）。信頼性ありの送り方（TCP・Steam の reliable）は、遅れが増えるので勧めません。
  • ルームに入っていない相手からのデータグラムは捨てる（よその人のパケットを上に渡さない）。
  • ほかのロビーのしくみも、ルームコードを「ロビーの属性」や「サーバーに渡すルームの名前」にすれば同じ形で載ります（下の「自前のリレー」「EOS P2P」の節がその例です）。

#自前のリレー（detphys_relay）

EOS も Steam も使わない時（自分のサーバーがある・コンソール・LAN の大会など）に、自分のサーバーに置ける小さな UDP のリレーです。DetPhys はサーバーの運営をしません。配るのはリレーのプログラムと置き方だけで、置くのは使う人です。

  • リレー: detphys_relay（C++ のプログラム 1 つ、Windows / Linux。コアにも Box2D にも頼らない）。ルームコードで 2〜15 人をつなぎ、中身は見ずに運ぶだけです。
  • Unity のパッケージの中のソース: Packages/dev.petaf.detphys/Tools~/detphys_relay/（ソースの 4 つのファイル・CMakeLists.txt・Dockerfile・systemd の設定・作り方の README）。フォルダをプロジェクトの外に写して作ります。
  • API: detphys_relay.h の detphys_link_create_relay（コアの DLL / .so に入っています。SDK は要りません）。手順はほかのトランスポートと同じです（作る → detphys_link_host / detphys_link_join → 毎フレーム detphys_link_poll）。
  • 経路（detphys_link_info.path）は DETPHYS_LINK_PATH_RELAYED。上乗せは 1 つのデータグラムに 1 バイトで、max_packet は 1199 B（再同期のかけら 1057 B は収まります）。
  • リレーを通しても結果（確定 tick のハッシュ）は同じです。リレーは中身を変えません。

#ゲームの側

detphys_relay_desc rd;
detphys_relay_desc_default(&rd);
rd.host = "relay.example.com";   /* 名前か IP アドレス（IPv4 / IPv6） */
rd.port = 40400;                 /* 0 = 既定の 40400 */
detphys_link* link = NULL;
detphys_link_create_relay(&rd, &link);   /* ここでは通信しない */
/* あとは「使い方」と同じ: detphys_link_host / detphys_link_join → 毎フレーム detphys_link_poll → role が決まったらセッション */
  • 名前を引く（DNS）のは最初の detphys_link_host / detphys_link_join の中で 1 回だけです（待つのでブロックします。「ルームを作る」「入る」を押した時に呼んでください）。引けない時は FAILED（理由 NETWORK）。
  • リレーとの往復は detphys_link_info.rtt_ms（1 秒ごとの PING）。相手との往復はセッションの detphys_rt_get_link_info で見ます。
  • 理由の読み方: NOT_FOUND（ルームが無い）・FULL・CODE_TAKEN（API が作ったコードなら自動で作り直す）・TIMEOUT（リレーから返事が無い・10 秒何も来ない）・PEER_LEFT（相手が出た。ホストが出たらルームごと閉じる）・NETWORK（名前を引けない・ソケット）・BACKEND（リレーの上限・バージョンの違い。detphys_link_error に説明）。
  • 設定（detphys_relay_desc）: local_port（自分のポートを決める。ふつうは 0）・hello_interval_ms（ルームの操作の送り直し、既定 250）・ping_interval_ms（既定 1000）・silence_timeout_ms（既定 10000）。
  • ブラウザ（wasm）からは UDP を送れないので、Web のゲームはこのリレーに直接つなげません（WebSocket / WebRTC の層が別に要ります。今はありません）。

#リレーを置く

置き場は UDP のポートを 1 つ開けられるサーバーなら何でもかまいません（安い VPS の 1 vCPU・メモリ 512 MB で足ります。1 ルーム 約 31 kbit/s なので、帯域と月の転送量でルームの数が決まります。下の「実測値」）。

まず、リレーのソースのフォルダ（Unity は Packages/dev.petaf.detphys/Tools~/detphys_relay）をプロジェクトの外（例 ~/detphys_relay）に写し、そのフォルダの中で下のコマンドを打ちます。同じ手順はフォルダの README.md にもあります。

Docker（Linux）: 写したフォルダの中で

docker build -t detphys-relay .
docker run -d --name detphys-relay --restart unless-stopped -p 40400:40400/udp detphys-relay
docker logs -f detphys-relay      # ルームの開け閉め・5 分ごとの数え上げ
  • イメージに入れるのはリレーのソースの 4 つのファイルだけです。中では root ではなく nobody で動きます。
  • 設定を変える時は、イメージの名前の後ろにオプションを並べます（docker run ... detphys-relay --port 40400 --max-rooms 200）。
  • ルームの数が多い時は --network host にすると Docker の NAT を通らないぶん軽くなります。

Docker を使わない（Linux）: g++ 1 回でビルドできます（C++17、標準ライブラリだけ）。

g++ -std=c++17 -O2 -pthread -I . relay_main.cpp relay_server.cpp -o detphys_relay
sudo cp detphys_relay /usr/local/bin/ && sudo cp detphys-relay.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now detphys-relay

Windows（Visual Studio 2019 以降）: 写したフォルダの中で cmake -S . -B build・cmake --build build --config Release を打つと build\Release\detphys_relay.exe ができます（CMake は Linux でも使えます）。外から受けるには、Windows のファイアウォールで UDP のポートの受信を許します（管理者の PowerShell で New-NetFirewallRule -DisplayName "DetPhys relay" -Direction Inbound -Protocol UDP -LocalPort 40400 -Action Allow）。

どこに置いても要ること:

  1. サーバー（VPS の管理画面のファイアウォール・セキュリティグループ・ufw など）で UDP 40400 の受信を開ける。
  2. ゲームに入れる名前（rd.host）を決める。IP アドレスのままでもよいですが、名前（DNS の A / AAAA）にしておくとサーバーを移せます。
  3. bucket（ゲームとバージョンの名前）をバージョンごとに変える（違うバージョンの人のルームが見えなくなる）。
  4. 立てたら、2 台でつないで、ログに room-open と room-close ... out_Bps=... が出ることを確かめる。

#リレーのオプション

オプション既定意味
--bind::待ち受けるアドレス。:: は IPv6 と IPv4 の両方（IPv6 が使えない所では自動で 0.0.0.0 にする）
--port40400UDP のポート（0 = OS が決める。--port-file に書く）
--max-rooms1000ルームの数の上限
--max-rooms-per-ip16同じ IP アドレスが作れるルームの数（0 = 上限なし）
--max-peers81 ルームの人数の上限（2〜15。DetPhys の API は今 2 人）
--room-kib-per-s / --room-burst-kib256 / 5121 ルームが運べる速さ [KiB/s] とその貯め。超えた分は捨てる（押し合いは 約 4 KiB/s なので 60 倍の余裕）
--hello-per-s10同じ IP からのルームの操作（作る・入る）の速さ。超えたら返事をしない
--peer-timeout-ms10000この間なにも来ないピアは出たことにする（API は 1 秒ごとに PING を送る）
--max-room-s01 ルームが続く時間の上限 [s]（0 = なし）
--stats-s60数え上げの行を書く間隔 [s]（0 = 書かない）
--verbose–ルームの出入りにアドレスも書く（ふつうは書かない）

ログ（標準出力。1 行 1 つ）: relay-listen ...（立ち上がった）・room-open id= bucket= code=・room-close ... why= secs= out_bytes= out_Bps= dropped_rate=（ルームごとの帯域）・stats rooms= peers= ... dropped=unknown:,rate:,bad: fwd_us=avg:,max:・final ...（Ctrl+C・SIGTERM で終わる時）。

#乱用よけと決まり

  • リレーはルームに入ったアドレスからのデータだけを、同じルームの相手にだけ運びます（知らないアドレスからのデータは捨てる）。API はリレーに connect するので、リレー以外からのパケットは受け取りません。
  • ルームの操作（作る・入る）は 96 B に詰めて送り、リレーの返事はそれより小さくしてあります（他人のアドレスを騙った頼みで、リレーから大きな返事を浴びせられない＝増幅しない）。PING と PONG も同じ大きさです。
  • アドレスが変わった時（携帯の回線・NAT のポートが変わる）は、次の PING（1 秒以内）のタグで付け直します。その間のデータは落ちますが、セッションが送り直します。
  • ルームコードは 10 万通りなので、知らない人が当てずっぽうで入ることはありえます（2 人で埋まったルームには入れません）。合言葉が要るゲームは、セッションの設定の照合（タグ）にゲーム側の値を足してください。
  • 時刻・アドレス・ルームコードはシミュレーションに入りません（リレーを通しても同じハッシュ）。

#プロトコル（自分でクライアントを書く人向け）

リレーのソースのフォルダの relay_protocol.h にすべて書いてあります（バージョン 1）。1 バイト目が種類で、0xD0 | 枠 がデータ（ピア → リレーは送り先の枠、0xF = 全員。リレー → ピアは送り主の枠）、それ以外は [種類]['D']['R'][バージョン] で始まるルームの操作（HOST・JOIN・PING・LEAVE / WELCOME・REJECT・PONG・PEER）。数は little endian です。

#実測値（PC i7-12700F・Galaxy S9 は Wi-Fi、2026-11-11）

  • 上乗せの遅れ: PC の中の往復で、直接の UDP より約 60 µs 長いだけです（リレーの中は 1 回 平均 19 µs）。PC ↔ S9（Wi-Fi）では、直接もリレーも往復 12〜22 ms で、Wi-Fi の揺れより小さい差でした。遠くに置いたリレーの遅れは、ほぼ「自分 → リレー → 相手」の経路の長さで決まります（同じ国の VPS なら片道 数 ms〜20 ms を足す見込み）。
  • 1 ルームの帯域（リレーが送った量、両方の向きの合計）: 押し合いで 約 31 kbit/s（1 秒に約 118 個・1 個 平均 33 B）、1 時間で約 14 MB。積み上げは再同期の時だけ大きくなります（70〜130 kbit/s）。
  • PC の中の 2 プロセスと、PC ↔ S9 の対戦（押し合い・動くステージ・積み上げ、取りこぼしや遅れを入れて）で、両方の確定 tick のハッシュが全部一致しました。
  • ルームの数の上限・同じ IP のルームの数を超えると BACKEND で断ります。帯域の上限（例 1 KiB/s）を超えた分は通しません。

#エンジンから使う（Unity・Godot）

同じインターフェースを Unity の C# と Godot（GDScript の GDExtension・C#）から使えます。手順はどのトランスポートでも同じです（作る → ルームを作る / 入る → 毎フレーム poll → 役が決まったらセッション）。

Unity（C#、DetPhys 名前空間）:

// ルームを作る側（ホスト = ピア 0）。入る側は host: false と code（打ったルームコード）
var room = new DetPhysRoomOpener(() => DetPhysLink.CreateRelay("relay.example.com"), host: true, bucket: "mygame/1.2");
// 毎フレーム
if (!room.Ready && room.Poll())
    session = DetPhysRtSession.CreatePush(settings, rules, meshes, room.Role, room.Link.Endpoint);
// room.Link.Info.RoomCode（ホストに出す 6 桁）・Info.Path（DetPhysLinkPath.Relayed など）・Info.RttMs（リレーまでの往復）
// 試合中も毎フレーム room.Link.Poll()。終わったら session → room の順に Dispose
  • DetPhysRoomOpener は、ゲストがホストより先に来た時（NotFound）に retryForMs まで入り直します（試験・自動の時に便利。人が打つ時は 0 にして「ルームが無い」と出す方がよい）。
  • 打ち間違いは DetPhysRoomCode.Parse(text, out code) で通信の前に分かります（CodeFormat / CodeCheck）。
  • テスト用のロビー（DetPhysLinkHub）で、1 プロセスの中で同じ流れ（ルームを作る → コードで入る → 対戦）を試せます。

Godot（GDScript）:

var link := DetPhysLink.relay("relay.example.com")          # port 0 = 40400
link.host_room("mygame/1.2")                               # 入る側は link.join_room(code, "mygame/1.2")
# 毎フレーム link.poll()。link.get_role() が 0 / 1 になったら（ホストは WAITING、ゲストは CONNECTED）
var m := DetPhysRtMatch.new(); add_child(m); m.start(link.get_role(), link)   # ノードが毎フレーム link.poll() を呼ぶ
print(link.get_room_code(), " ", link.get_info()["path_name"])   # 例 "529371 RELAYED"
  • DetPhysLinkHub.create(...) と hub.create_link() でテスト用のロビー。DetPhysLink.room_code_check(text) で打ち間違いを先に見る。
  • 入り直し付きの手順はサンプルの samples/common/detphys_sample_room.gd（Unity の DetPhysRoomOpener と同じ動き）。C# の層は DetPhysLink.CreateRelay・DetPhysLinkHub・DetPhysRoomCode・DetPhysRoomOpener（addons/detphys/csharp/DetPhysLinks.cs。Unity と同じ使い方）。

サンプル（Unity の PushVersus / StackVersus、Godot の push_versus / stack_versus）は、既定では LAN の UDP でつなぎます。メニューの「リレー」に host か host:port を入れて「ルームを作る」と、ルームコードが出ます。もう片方は同じリレーとルームコードを入れて「ルームに入る」を押します。

起動の引数: relay=<host>[:<port>]・room=<ルームコード>・roomseed=<n>（テスト用。両方に同じ n で決まったルーム）・bucket=（既定 detphys-sample/push・detphys-sample/stack）・localport=。

#実測値（Unity 6000.3・Godot 4.7.2 .NET、PC i7-12700F・Galaxy S9 は Wi-Fi、2026-11-11）

  • PC に立てたリレーを通して、Unity ↔ Godot（PC どうし、PC ↔ S9）で押し合い 1800 tick（両方に遅れ 30〜60 ms・取りこぼし 10%・重なり 2%）と積み上げ 120 ターンを、どちらがホストでも回しました。両方の確定 tick のハッシュと勝敗が全部一致しました。
  • ゲストがホストより先に来ても、入り直して 2 秒以内に役が決まりました。
  • 押し合いで 1 つの側がリレーへ送ったのは 30 秒で約 57 KB（1 tick 33 B）です。

#エンジンから使う（Unreal）

Unreal の層（プラグイン DetPhys）も同じインターフェースを包みます。Blueprint からも C++ からも呼べます。

  • 手順: UDetPhysLink::CreateRelay(Outer, Host, Port, LocalPort) → HostRoom か JoinRoom → 毎フレーム Poll → GetRole() が 0 / 1 になったら、それを LocalPeer にしてセッション（UDetPhysRtSession::CreatePush など）に link を渡します。

// C++（Blueprint も同じノード）

M->OnRoomReady.AddDynamic(this, &AMyActor::HandleRoomReady);  // (Role, RoomCode, Link)。ホストは RoomCode を画面に出す
M->OnTickConfirmed.AddDynamic(this, &AMyActor::HandleTick);   // (Tick, Hash, Flags)。両方のピアで同じ Hash
// 毎フレーム M->LocalInput = UDetPhysLibrary::MakePushInput(Move, bJump, bDash);
  • サンプル: 押し合いのマップ PushVersus・PushComponents（コンポーネントだけで組んだもの）・コマンドレット -run=DetPhysVersus（積み上げも）で、起動の引数 relay=・room=・roomseed=・bucket=・localport= が Unity・Godot と同じに使えます。

  • PC に立てたリレーを通して、Unreal ↔ Unity・Unreal ↔ Godot で押し合い 1800 tick（両方に遅れ 30〜60 ms・取りこぼし 10%・重なり 2%）と積み上げ 120 ターンを、どちらがホストでも回しました（コマンドレットと、コンポーネントで組んだマップの両方）。両方の確定 tick のハッシュと勝敗が全部一致しました。
  • ルームを作ってから役が決まるまで、コマンドレットで 1〜3 ms、マップ（Tick で回す）で約 0.5 秒でした。
  • プラグインの自動テスト DetPhys.Sample.Link（ルームコード・テスト用のロビー・リレーの時間切れ・コンポーネント 2 つの対戦）を、Session Frontend の Automation から回せます。

#EOS P2P

Epic Online Services の P2P（無料。NAT 越えと、越えられない時のリレーは EOS 側）を、このインターフェースに載せます。自分のサーバーは要りません。このバージョンでは、Unity・Godot の Windows・Android と、Unreal の Windows で使えます。

  • EOS SDK は同梱しません。Epic の開発者ポータルから取ってください。DetPhys は Epic Games とは無関係で、公認されたものではありません。
  • ポータルで作る値（ゲームに埋め込む値）: 製品 ID（Product ID）・サンドボックス ID（Sandbox ID）・デプロイメント ID（Deployment ID）・クライアント ID（Client ID）とクライアントのシークレット（Client Secret）。クライアントのポリシーは P2P と Lobby が使えるもの（Peer2Peer）にします。ログインはデバイス ID で行うので、遊ぶ人に Epic のアカウントは要りません。
  • 使い方: detphys_eos.h（別のライブラリ detphys_eos）の detphys_eos_desc_default で既定を入れ、ポータルの値を入れて detphys_eos_link_create でトランスポートを作ります。あとはほかのトランスポートと同じで、ホストは detphys_link_host、ゲストは detphys_link_join、毎フレーム detphys_link_poll です。作れなかった時の説明は detphys_eos_last_error、プロセスの終わりに detphys_eos_shutdown を 1 回呼びます。
  • ログインはプロセスで 1 回: 最初のトランスポートを作った時に EOS を初期化し、デバイス ID でログインします（poll の中で進むので、ログインを待たずに host / join を呼べます）。トランスポートを壊してもログインは残るので、2 つ目からはすぐルームの操作に入ります。同時に使えるトランスポートは 1 プロセスに 1 つです。
  • つなぎ方: ホストは EOS の Lobby（2 人まで。bucket = Lobby の BucketId、ルームコード = Lobby の属性）を作り、ゲストは同じ bucket とルームコードの Lobby を探して入ります。P2P の経路はゲストが申し込み、ホストが受けます。NAT を越えられない時は EOS のリレーに落ちます。detphys_link_info.path は自分の側から見た経路で、どちらか片方が DETPHYS_LINK_PATH_RELAYED なら、間に EOS のリレーが入っています。リレーでも結果（ハッシュ）は同じです。
  • 作ったばかりのルームは、検索に出るまで少しかかることがあります。ゲストが NOT_FOUND になったら、少し（0.5 秒ほど）待ってトランスポートを作り直し、入り直してください（ログインは残っているので速く進みます）。
  • 1 つのデータグラムは 1170 バイトまで（EOS の上限。detphys_link_info.max_packet）。DetPhys のセッションでいちばん大きいのは再同期の状態のかけらで、約 1060 バイトなので収まります。
  • リレーの使い方（detphys_eos_desc.relay）: DETPHYS_EOS_RELAY_ALLOW（既定。直接つながらない時だけリレー）・DETPHYS_EOS_RELAY_FORCE（必ずリレー。リレーの時の動きを試す）・DETPHYS_EOS_RELAY_NEVER（リレーを使わない。直接つながらなければ NETWORK で失敗）。
  • 1 台で 2 人を試す: デバイス ID は「この端末・この OS のユーザー」に 1 つなので、同じ PC の 2 つのプロセスは同じ EOS のユーザーになり、つながりません（ゲストが LOGIN で失敗します）。2 つ目のプロセスだけ flags に DETPHYS_EOS_FLAG_NEW_DEVICE_ID を付けると、デバイス ID を作り直して別のユーザーになります。ゲームでは使わないでください（遊ぶ人が毎回別のユーザーになります）。
  • Android: EOS SDK は Java の側の準備が要ります。トランスポートを作る前に、アプリの Activity で System.loadLibrary("EOSSDK") と com.epicgames.mobile.eossdk.EOSSDK.init(activity) を呼んでください（していないと作る時に BACKEND になり、説明に EOS_Android_JavaVMNotStored と出ます）。EOS SDK の aar（eossdk-StaticSTDC-release.aar）と、aar が使う AndroidX（androidx.browser・androidx.core・androidx.security:security-crypto）を Gradle で入れ、INTERNET と ACCESS_NETWORK_STATE の権限を付けます。cache_dir には Context.getFilesDir() などを渡せます。
  • iOS: このバージョンでは使えません（Unity・Godot では、iOS で DetPhysEos.IsAvailable が false）。
  • SDK の置き場所（コアを自分でビルドする時）: Epic の zip の中の SDK フォルダを sdk/eos/SDK に置き（sdk/eos/SDK/Include/eos_sdk.h になる形）、Android・iOS 用の zip も同じ SDK フォルダに重ねます（Android は中の aar から libEOSSDK.so を取り出してリンクします）。CMake の DETPHYS_EOS は既定で AUTO（SDK があれば作る、無ければ外す）です。必ず作る時は ON にします（SDK が無ければ configure が止まります）。別の場所なら -DDETPHYS_EOS_SDK_DIR=<SDK フォルダ> を渡します。Windows は MSVC か clang-cl の x64 で作ります。

#Unreal から使う

EOS のトランスポートも、ほかのトランスポートと同じ UDetPhysLink です（ルームを作る / 入る → 毎フレーム Poll → 役が決まったらセッション）。違うのは作る所だけです。

  • Unreal に入っている EOS とは別のものです。Unreal の Online Subsystem EOS・EOS Shared のプラグインは使わず、DetPhys の detphys_eos が EOS SDK を直に呼びます。同じゲームでそれらのプラグインも EOS を初期化すると、EOS SDK の DLL を 2 つの所から読むことになり、正しく動きません。DetPhys の EOS を使う時は、それらのプラグインを有効にしないでください。
  • 置くファイル: EOSSDK-Win64-Shipping.dll（自分の EOS SDK の SDK/Bin）を、プロジェクトの Binaries/Win64 に置きます（書き出したゲームでは実行ファイルの隣）。DetPhys の EOS の部分（detphys_eos.dll）はプラグインに入っています。EOS SDK の DLL が無い時も、ほかのトランスポートはそのまま動きます。使えるかは UDetPhysEos::IsEosAvailable()、使えない理由は GetEosError() で分かります。
  • 対応している端末: このバージョンでは Windows x64 だけです（Android・iOS は IsEosAvailable() が false を返します）。
  • ポータルの値: FDetPhysEosSettings に入れるか、ini ファイル（[eos] の ProductName・ProductVersion・ProductId・SandboxId・DeploymentId・ClientId・ClientSecret）から LoadEosSettings で読みます。FindEosSettingsFile はプロジェクトの Saved・プロジェクトのフォルダ・実行ファイルのフォルダの detphys_eos.ini を探します。ClientSecret はアセットやマップに保存されません（Transient）。実行時に ini から読むか、コードで入れてください。クライアントのシークレットはバージョン管理に入れないでください。
  • 同時に使える EOS のトランスポートは 1 つです。UDetPhysLink::Close を呼ぶと EOS のトランスポートはその場で片付き、すぐ次のものを作れます（最後の GetInfo・GetLinkError は読めるまま）。UDetPhysRoomOpener の入り直しも、前のものを閉じてから作り直します。

M->StartRoom(UDetPhysEos::OpenEosRoom(M, Eos, /*bHost*/ true, TEXT(""), M->RoomBucket));   // 入る側は bHost = false と Code
M->OnRoomReady.AddDynamic(this, &AMyActor::HandleRoomReady);   // (Role, RoomCode, Link)。ホストは RoomCode を画面に出す
  • UDetPhysEos::OpenEosRoom は、ゲストがホストより先に来た時に 60 秒まで 1 秒ごとに入り直します（RetryForMs・RetryEveryMs で変えられます）。セッションを自分で作る時は UDetPhysEos::CreateEosLink(Outer, Settings) で link を作り、HostRoom / JoinRoom を呼びます。
  • 終わる時に EOS を片付けるなら、全部の EOS のトランスポートを閉じてから UDetPhysEos::ShutdownEos() を 1 回呼びます（その後、同じプロセスでは EOS をもう使えません）。
  • サンプル: メニューの「押し合い」「押し合い（コンポーネントで組んだもの）」「3D の押し合い」に「ルームを作る（EOS）」「ルームに入る（EOS）」があります（ルームコードの欄はリレーと同じ）。detphys_eos.ini はプロジェクトの Saved かプロジェクトのフォルダに置きます。起動の引数は Unity・Godot と同じで、eos=<ini のパス、ini のあるフォルダ、または 1>・eosrelay=allow|force|never・room=・roomseed=・bucket= です。コマンドレット -run=DetPhysVersus では積み上げでも使えます。

実測値（UE 5.8.4・EOS SDK 1.19.2.1、PC i7-12700F・Windows 11 の Unreal〔頭なし〕、Galaxy S9・Android 10・Wi-Fi の Godot 4.7.2 と Unity 6000.3、2026-11-12）:

  • Unreal ↔ Godot（押し合い・Godot がホストの押し合い・3D の押し合い・積み上げ・コンポーネントで組んだ押し合い）と Unreal ↔ Unity（押し合い・3D の押し合い）で、確定 tick のハッシュと勝敗が全部一致しました（押し合いは両方に遅れ 30〜60 ms・取りこぼし 10%・重なり 2% を入れて 1800 tick、3D は 1800 tick、積み上げは 120 ターン）。経路はどれも直接でした。
  • ルームを作ってから役が決まるまで（ログインを含む）2.6〜6.6 秒、入り直しは要りませんでした。送る量は押し合いで 1 tick 34〜48 B（遅れなどを入れた分を含む）、3D で約 33 B です。Unreal の 1 フレームのコアの時間は平均 0.14〜0.15 ms でした。

#Steam（予定）

Steam のトランスポート（Steam の Networking Messages とロビー）は、このバージョンには入っていません。今 Steam で遊べるようにするには、Steamworks の Networking Messages で自分のトランスポートを detphys_transport に書くか（上の「自分のトランスポートの書き方」）、EOS P2P か自前のリレーを使ってください。DetPhys は Valve とは無関係で、公認されたものではありません。
