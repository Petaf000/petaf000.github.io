パフォーマンス

ロールバックでいちばん重いのは「予測が外れた時に、N tick 戻して N tick 計算し直す」所です。DetPhys は、これを 1 フレームの予算に収まるかで目安を決めています。体の数と予測の上限 N は開発者が設定で変えられます。下の数字を見て、自分のゲームの体の数・形・N を決めてください。

#目安（1 フレーム 4 ms に収める）

端末目安
中位の PC60 Hz・凹形状の動くボディ 200 体・N = 10（1 フレームで 10 tick 再計算）で 4 ms 以内
モバイル（Galaxy S9 級）ベイクした凹形状 60 体・N = 10、または 100 体・N = 6 で 4 ms 以内
  • 測った端末: PC = Core i7-12700F / Windows 11 / 電源プラン「高パフォーマンス」、Galaxy S9 = SC-03K / Snapdragon 845 / Android 10。
  • 「1 フレーム」= N tick 前に戻す → N tick 再計算（各 tick で snapshot のリングに dyn の snapshot）→ 1 tick 進める、を 300 フレーム平均したもの。全部のボディが起きている、いちばん重い状態です。
  • 実際の対戦では、予測が外れる回数も、外れた時に戻す tick 数もずっと少なく、平均はこの何分の 1 かです（下の「実際のセッション」）。

#3D の動く凹形状

detphys3d_kinematic.h の 2 つのシーン。60 Hz・4 サブステップ・重力 −10 m/s²・ワーカー 1・分割は既定（最大 4 回・20 mm）・full の snapshot。PC = Windows x64・msvc-x64 Release、S9 = Galaxy S9（SC-03K・Android 10）android-arm64。どちらもコアを固定していません。

  • シーン a: 回る凹の歯車 1 個（八角の台＋仕切り 3 枚＋外周の壁 12 枚、1.2 rad/s。外周の壁の角まで半径 3.26 m なので毎 tick 4 回に分割）。
  • シーン b: 動く足場 4 個（止まりながら往復・リフト・円を回る・ゆれる。どれも凹の皿。分割なし）。

#エンジンの層の負荷

116 体のシーンを作り、600 tick 進めてハッシュを取るまで: Unity のエディタ 14〜16 ms（2022.3 も 14.5〜15.3 ms）・S9 の APK 54〜58 ms、Godot（ヘッドレス）15〜17 ms・S9 55〜75 ms、Unreal（UE 5.8.4 のエディタ、-nullrhi）14.7 ms。どのエンジンでもハッシュは同じです。

#調整できる設定

つまみ効き方
体の数・凸多角形の数いちばん効く。ベイカーの epsilon_px を上げると凸多角形が減る
予測の上限 N（max_prediction）小さいほど 1 フレームの最大が軽い。小さすぎると遠い相手で待ちが増える
入力の遅延・入力遅延の自動調整予測が外れる回数を減らす（遅延 0 の手触りと引き換え）
ワーカー（worker_count）凹形状 200 体ほどで効く。少ない・単純な形では 1 本の方が速い。ハッシュは変わらない
snapshot の種類リアルタイムは dyn（既定）が速い。base の数（snapshot_base_slots）は形がよく変わるなら増やす
照合の間隔（hash_interval）既定は毎 tick。ハッシュを作る時間はわずか
動く凹形状の分割（max_subticks・subtick_move_mm）分割した tick はその回数分重い。動きを遅くするか、分割を減らすと軽い（すり抜けの速さとの引き換え）。3D は形の外接半径でいちばん速い点を数えるので、大きく回る台ほど分割が増える
desync デバッガーOFF（既定）なら 0。ON で記録 5〜20 µs / tick（3D の約 70 体は PC 15〜19 µs・S9 約 175 µs / tick）
