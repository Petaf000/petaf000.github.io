Sample: Gear Arena (pushing inside a spinning gear)

A match inside a spinning gear: push concave pieces around. It exists for both Unity and Godot, and the two can play each other.

  • Moving concave shapes, collided exactly: an internal gear (a concave ring with two gaps) spins; inside it, two rods push 120 concave pieces (L, T, U, cross). The gear is a kinematic concave shape driven as a function of the tick ("moving concave shapes" in 3. Concepts), so it adds no state to roll back.
  • Zero input delay: the default input delay is 0 ticks. The remote input is predicted; a wrong guess is rolled back and re-simulated.
  • Cross-engine play: the rule is written once in C#; the same files are in Unity (GearArena/Runtime/Shared in the imported samples) and Godot (samples/gear_arena/shared). Unity on a PC and Godot on Android agree on every confirmed tick's hash.
  • A desync shows its cause and heals itself: "Nudge 1 ULP" shifts the state by one ULP; the desync debugger shows the tick, body and field on both devices and the session resyncs.

How to play: a piece that falls out through a gap and crosses the line below scores for the player on the other side (falls on P1's side, left = a point for P2). After 30 seconds (1800 ticks) the player who pushed out more wins.

#Play in a room

Instead of the LAN UDP (typing the peer's IP), the two devices can also connect with a room code. Then the peer does not have to be on the same Wi-Fi (a home line and a mobile network, for example). There are two ways, "relay" and "EOS", and the menu has a "Make a room" and an "Enter the room" button for each. The match is the same as on a LAN, between Unity and Godot and between a PC and Android too.

Steps:

  1. On the host, make a room: the 6-digit room code appears in the middle of the match screen while it waits for the peer. Tell the other player this code.
  2. On the guest, enter the room code. While it connects, "Cancel" ("Menu" when the Unity sample was opened without the sample picker) goes back to the menu.
  3. When the peer is in, the match starts and the room code disappears. The path line is below the panel at the top left.
  • The room code has 6 digits (5 digits plus a check digit). Typos are found before anything is sent: "The room code is not valid".
  • The path is how this side reaches the peer: DIRECT = directly, RELAYED = through a relay. A relay room is always RELAYED. With EOS, if either side shows RELAYED, EOS's relay is in between. The confirmed ticks' hashes are the same on every path.
  • The EOS transport does not measure a round trip time to a relay, so with EOS the path line shows no round trip time.
  • The room's bucket is detphys-sample/gear by default. Use the same one on both sides (with different buckets the guest cannot find the room).

#Relay setup

  • Run detphys_relay somewhere both devices can reach (a VPS, or a PC on the same LAN for a quick test) and allow incoming UDP on its port (40400 by default). See 8. Transports and room codes.
  • Enter the same host or host:port under "Relay" on both devices.

#EOS setup

  • The EOS SDK is not included. Get it from Epic's developer portal and add EOSSDK-Win64-Shipping.dll (Windows) and eossdk-StaticSTDC-release.aar (Android) (Unity: Assets/Plugins/x86_64, Assets/Plugins/Android; Godot: addons/detphys/bin/windows, addons/detphys/eos/android. For Godot on Android, enable the DetPhys plugin in the project settings and export with the Gradle build). Details: Using it from Unity and Godot.
  • Add detphys_eos.ini with your portal values (ProductName, ProductVersion, ProductId, SandboxId, DeploymentId, ClientId, ClientSecret in [eos]). On a PC it goes next to the executable, or in Application.persistentDataPath (Unity) / user:// (Godot), which is the place to use when running in the editor; on Android, in the app's external files folder (/sdcard/Android/data/<package>/files/).
  • Keep detphys_eos.ini out of version control (it holds the client secret). For the sample, put it only on the devices you test with. In your own game the values ship with the game (EOS P2P).
  • Test EOS rooms with two devices. Two processes on the same PC are the same EOS user, so they cannot connect.
  • When a file is missing, the menu shows "EOS is not available: ..." with the reason. The LAN and relay rooms still work.

Launch options (rooms): relay=<host>[:<port>] or eos=<ini path, its folder, or 1> (1 = look in the usual places) use a room instead of the LAN UDP. The side with room=<room code> or peer=1 enters; the other side makes the room. Also roomseed=<n> (tests: the same n on both sides uses a fixed room code, and the guest tries again until the room exists), bucket=<name>, localport=<n> (this side's port with a relay), eosrelay=allow|force|never (how EOS's relay is used; EOS P2P). With auto=1 or roomseed=, a relay guest also tries again for 30 seconds until the room exists.
